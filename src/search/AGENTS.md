# src/search/ — vault search: companion client, chunker, index lifecycle

Local instructions for the search leg: `SearchManager.ts`, `client.ts`, `chunker.ts`,
`debounce.ts`, `lifecycleGate.ts`, `types.ts`, plus the server half in
`scripts/search-companion.mjs`, its `Dockerfile`/`docker-compose.yml`/`.dockerignore`, and the
tests `tests/searchCompanion*.test.mjs` / `tests/searchVaultIsolation.test.mjs`. The root
`AGENTS.md` is the canonical contract; this file adds what is only true here.

Related areas: the embedding/rerank provider clients are `src/providers/AGENTS.md`; the
container serving local models is `/home/_shared_code/inference-engine/llama/AGENTS.md` (inference-engine repo); the indexing jobs run on
the queue described in `src/orchestration/AGENTS.md`. User-facing writeup:
`docs/search-companion.md`.

**Client/server version pairing:** `SCHEMA_VERSION` (`scripts/search-companion.mjs`) and
`SEARCH_REQUIRED_SCHEMA_VERSION` (`src/search/types.ts`) are **bumped together**, always in the
same commit. Both are **7** today. A companion reporting a lower `schemaVersion` is flagged
`rebuildRequired` (health `ok: false`), so a landing that bumps them must rebuild the companion
image in the same change.

**Measurement artifacts** cited below live in the eval-harness archive
(`/home/_shared_code/eval-harness/local-inference-bench/measurements/`), not in this repo —
`runs/` is scrubbed and `.gitignore`d here. Re-run measurements into a new sibling dir there.

## Quirks index

The one-line hooks below say *where to walk*, not what to do — read the full entry before acting.

- The search companion's container image has no `npm install` step and needs `node:24-slim` minimum.
- The companion's listen host defaults to loopback everywhere except inside the container.
- The companion's pooling CTE must stay `MATERIALIZED`; its FTS schema migrates itself.
- Counting vault notes by globbing `*.md` is wrong by ~7.7x — archived queue job files dwarf the real corpus.
- The search client has two timeouts on purpose; a mid-operation failure must not latch the availability gate.
- The interactive search timeout drives a third, request-scoped budget: the companion's cooperative deadline.
- The cooperative deadline starts at the client's `sentAt`; the backfill yields to interactive searches; the matrix invalidates once per flush.
- Companion search latency is governed by how much of the index the query matches, not by index size.
- Obsidian's "Excluded files" list is honored asymmetrically: search hides those paths, the file-open palette deranks them.
- The vector leg is dimension-agnostic by design and scans the full matrix by requirement — every number below is measured.
- A chunk id is unique only within a vault; every companion statement must key on `(vault_id, id)`.
- `embedding_space` is a conservative guard, not evidence that precision changes the vector space.
- Quantization degrades spread, not ranking — Q2_K still retrieves perfectly.
- FTS5's implicit AND is per chunk, not per document — root cause of the "matt pocock" class of misses.
- The entity facet (schema 7): frontmatter `author` reaches FTS as a dedicated `entities` column on every chunk.
- The search query log lives outside the vault's note tree, so it cannot be indexed by construction.
- Linked-post chunks (pf-3): a source note ranks on the text of the notes it stamp-links, as ordinary chunks.
- Superseded interactive searches are recallable end to end: client-side abort, companion-side pre-flight abandon, deadline skew guard.
- Companion code ships only via an image rebuild (`home-compose up crucible-search`) — a bare restart runs stale code.
- `POST /v1/paths` is the enumeration endpoint the audit/reconcile pair depends on — a hard read/write boundary.
- The tag boost is client-side and frontmatter-only; keyword-dump queries are a structural non-goal; rerank stays a manual action.

## Quirks

- **The search companion's container image has no `npm install` step, and the base tag must never drop below `node:24-slim`.** `scripts/search-companion.mjs` imports only Node builtins — including `node:sqlite` (`DatabaseSync`), which is unflagged starting Node 23.4 and is what the FTS5 index runs on. Because the server has zero npm dependencies, the `Dockerfile` copies only the facade (`scripts/search-companion.mjs`) plus the `scripts/search-companion/` module directory (rem-R3 decomposition — the `COPY` lines and the `.dockerignore` allowlist must track that module tree) and skips `package.json`/`node_modules` entirely; adding an install step or downgrading the base image below 24 breaks the `node:sqlite` import silently (it throws at the `import` line, not at some later call site). Don't "helpfully" add a `package.json` copy or an install step just because that's the usual shape of a Node Dockerfile — this one is dependency-free by design. **`.dockerignore` is load-bearing for the same reason**: without it the build context drags in `node_modules/`, the 2.8 MB `main.js`, and the multi-hundred-MB `.crucible/search.sqlite`, none of which the image needs.

- **The companion's listen host defaults to loopback (`127.0.0.1`) everywhere except inside the container.** `scripts/search-companion.mjs` reads `--host` → `CRUCIBLE_SEARCH_HOST` → `'127.0.0.1'`, and the standalone `npm run search:serve` path relies on that default staying loopback-only — the API is unauthenticated with full index write access, so a loopback bind is the whole security boundary for a bare `node scripts/search-companion.mjs` run. Only the `Dockerfile`/`docker-compose.yml` set `CRUCIBLE_SEARCH_HOST=0.0.0.0`, because a loopback bind *inside* a container is unreachable from the host even with a published port — that's a container-only override, not a new default. Don't flip the script's own default to `0.0.0.0` to "simplify" the container case; that would silently expose every non-containerized run.

- **The companion's pooling CTE must stay `MATERIALIZED`, and its FTS schema migrates itself.** `/v1/search` ranks one row per *path*, not per chunk: a `matched` CTE scores chunks with weighted bm25 (`bm25(chunks_fts, 0,0,0, 10.0, 5.0, 1.0, 8.0)` — title ≫ entities ≫ heading ≫ text; the trailing 8.0 is schema 7's `entities` column, appended *last* because `snippet(chunks_fts, 5, …)` addresses the snippet column by index), then a `pooled` CTE collapses to `GROUP BY path` on `MIN(score_text)`. Three non-obvious things hold it together. (1) **`WITH matched AS MATERIALIZED` is load-bearing, not a hint** — without it SQLite flattens the CTE into the aggregate query and `bm25()`/`snippet()` throw `unable to use function bm25 in the requested context`, because FTS5 auxiliary functions are illegal in an aggregate context. (2) The winning chunk's `id`/`heading`/`snippet` ride along for free because SQLite takes bare columns from the row that produced the `min()` when a query has exactly one `min()`/`max()` aggregate — a second aggregate (`COUNT(*)`) doesn't break that, but adding a second `min()`/`max()` would. (3) `COUNT(*) OVER ()` is evaluated before `LIMIT`, which is what let the duplicate `COUNT(*) MATCH` query (it doubled FTS work on every search) go away while `total` stayed the distinct-path match count. Separately, `chunks_fts` now carries FTS5 `prefix='2 3'` (introduced at schema version **2**), which `CREATE VIRTUAL TABLE IF NOT EXISTS` will *not* retrofit onto an existing database — so `migrateFtsSchema` drops and refills the FTS table from `chunks` on startup (lossless: `chunks` holds every indexed column). The client's half of that contract is `SEARCH_REQUIRED_SCHEMA_VERSION` in `src/search/types.ts`: a companion reporting a lower `schemaVersion` is flagged `rebuildRequired` (health goes `ok:false`, so auto-indexing defers; search still runs and says "index rebuild required"), because an older *binary* is the one mismatch no server-side migration can fix. Bump both together. Finally, the companion exports its pure helpers and guards the server bootstrap behind `isMainModule()` so `tests/searchCompanionRanking.test.mjs` can import it without opening a database or binding a port — keep new side effects inside `startServer`.

- **Counting "how many notes are in the vault" by globbing `*.md` is wrong by ~7.7x here — the queue's archived job files dwarf the real corpus.** `_crucible/orchestration/queue/{done,failed}` accumulated one markdown file per orchestration job (17,206 done + 2,027 failed at the time of writing), so the vault's 42,042 `md`/`qmd`/`txt` files were **37,081 job files** plus only **~5,456 genuinely indexable notes**. (Since thq WP-8, 2026-07-30, jobs live in the plugin's SQLite DB and no new job files are created — but the folder is a frozen archive that keeps inflating file counts until the user deletes it on disk.) `_crucible` is search-excluded by default (`defaultExcludedFolders` in `src/exclusions.ts`), so `SearchManager.listIndexableFiles` correctly reports the small number — a full rebuild enqueuing ~55 jobs rather than the expected hundreds is the *right* answer, not a truncated scan. The file-open-palette plan was sized against the inflated figure and set `SEARCH_REBUILD_BATCH_FILES = 250`; it is now 100 (`src/orchestration/workflows/SearchIndexWorkflow.ts`). Two traps when re-measuring: use `find -L` (the vault symlinks `docs/` and every `initiatives/*/{README.md,INITIATIVE.md,FEEDBACK.md,plans}` in from their repos — plain `find` misses ~495 files Obsidian indexes), and remember `SearchManager.indexFiles` returns `upsertedFiles`, i.e. files whose **content hash changed**, so a job reporting "58 files" out of a 250-path batch is reporting a mostly-unchanged re-run, not dropped work.

- **The search client has two timeouts on purpose, and a mid-operation failure must not latch the availability gate like a failed probe.** `src/search/client.ts` keeps the interactive `SEARCH_SERVICE_TIMEOUT_MS` (5s, health + search — the UI must stop waiting on a dead companion) separate from `SEARCH_SERVICE_INDEX_TIMEOUT_MS` (60s, reset/upsert/delete/fileStates). Do not collapse them back into one constant: an upsert carries hundreds of chunks and is issued from the same main thread that synchronously chunks the batch's files, so the timeout races *local* work, not just the server's — under the old uniform 5s a healthy container (measured: ~53ms per 500-chunk flush server-side at the time, 0 restarts, clean logs — re-measured 2026-07-26 at ~17s per 500-chunk flush against the grown 53k-chunk index, because the upsert's per-chunk `chunks_fts` delete keys on UNINDEXED columns and full-scans the FTS index, O(index size) per chunk; see the wp3-throughput-2026-07-26 eval-harness measurement. That growth is exactly why the 60s indexing timeout must not be "simplified" back down) was declared unreachable partway through the first full rebuild. The second half of that failure was the latch: `markCompanionOffline` used to call `markOffline`, whose `SEARCH_OFFLINE_CACHE_MS` is **5 minutes**, so one spurious timeout made every remaining batch job defer *without ever asking the companion again*, and each Obsidian reload drained exactly one more batch. Mid-operation failures now go through `CompanionAvailabilityGate.markTransientFailure` (`SEARCH_TRANSIENT_OFFLINE_MS`, 5s — both constants in `src/search/lifecycleGate.ts`) and carry the thrown message as the gate's reason — without it `searchDeferredResult` falls back to "not reachable at <url>. Start it with: home-compose up crucible-search", which sends the user to restart a container that is already healthy. Keep `markOffline` for probe-confirmed outages only. Relatedly, `scripts/search-companion.mjs` now `console.error`s before returning its catch-all 500: the client turns any 5xx into `SearchServiceUnavailableError` → "companion not reachable", so a request that failed on its own merits used to be indistinguishable from a down container while `docker logs` showed nothing at all.

- **The interactive search timeout is now the `searchQueryTimeoutMs` setting (default 4000ms, UI floor 3000), and it drives a *third*, request-scoped budget: the companion's cooperative deadline — added because the measured cause of "long queries time out at 5s" was queuing, not query cost.** WP-2 (clsl, eval-harness `measurements/clsl-wp2-search-latency-2026-07-29/`, 28,706-chunk / 2,534-path copy of the live index — note the index had shrunk from the 52,257-chunk figure the latency table below was measured at) instrumented the exact repro query (15 terms, zero strict-AND hits): total **674–800ms** server-side, of which the **zero-hit loose-OR rescue is ~65% (~435–454ms)** — one monolithic re-run of the full bm25/snippet/pooled statement — and the coverage leg ~225–290ms (common terms dominate); a 9-term query that *does* hit strict-AND runs ~100ms. Extrapolated worst case ~1.4s: **a single query cannot reach 5000ms by itself** — the real producer is the request queuing behind an upsert flush on the single-threaded companion. Since commit `9b0bb9b` split flushes into ~100-chunk sub-transactions with a `setImmediate` yield between them, a queued request waits behind **one sub-batch (~3.4s at the measured ~17s/500-chunk throughput), not the whole flush** — still able to breach an interactive budget on a slow day, which is what the deadline bounds — though note the residual gap this entry originally carried (the deadline clock started at handler-run time, blind to the queue wait itself) is closed by the rsp entry below: the deadline now starts from client `sentAt`. Mechanics (all clsl-wp5): `SearchServiceClient.search(options, timeoutMs)` sends `budgetMs` = 80% of whichever timeout is in effect (`SEARCH_QUERY_BUDGET_FRACTION`); the companion clamps it to [500, 20000] (default 3200 when absent) and checks `overBudget()` **between statements, never inside one** — the load-bearing checkpoint is a *pre-flight gate on the rescue* (no internal checkpoint is possible in a monolithic statement), plus gates around the vector leg, the blend fallback, and between coverage-leg term scans (early-stop can only undercount a path's coverage, safe for an additive leg). Over budget ⇒ well-formed partial response with additive `degraded: true`; in budget ⇒ byte-identical to the pre-deadline shape, and old client/old server pairings degrade cleanly (`normalizeSearchResponse` maps absence to `undefined`, never `false`). Two guard rails on top: `CompanionAvailabilityGate.noteInteractiveSearchResponse()` resets the consecutive-probe-timeout streak whenever a real `/v1/search` response arrives — so one slow interactive query hogging the single thread can no longer feed three probe timeouts into the 5-minute `markOffline` latch, while a genuinely dead companion (which never produces a response) still escalates on schedule — and a timed-out search leaves a `logWarn` breadcrumb with elapsed ms + term count. The two-timeout law above still stands: `searchQueryTimeoutMs` threads only into the interactive budget; health probes keep the hardcoded 5s and indexing keeps 60s. The flagged follow-up (separate plan, not landed): cap the *rescue's* OR clause rarest-first — WP-2 re-scoped that lever from the coverage leg to the rescue, since the rescue is where the cost actually is.

- **The cooperative deadline starts at the client's `sentAt`, the backfill yields to interactive searches, and the matrix invalidates once per flush — the rsp sprint's three-part fix for "the first search during a backfill times out; the retry works."** Root cause of that exact repro (`runs/dispatch/feedback-search-first-run-investigation.md`): the companion stamped `deadlineAt` at handler-run time, *after* `await readJson` — so a request queued ~3.4s behind an upsert sub-batch burned most of the client's 4s timer before the deadline clock even started, the companion finished "comfortably in-budget," and `degraded: true` was structurally unreachable for the real failure mode. (The query *embed* runs before the client timer starts and is deliberately outside it — a cold embedder adds felt latency but cannot cause the timeout; the `embedMs` field in the timeout `logWarn` breadcrumb exists so log triage can tell the two apart.) The fix stack, all in `scripts/search-companion.mjs` + `src/search/client.ts`: (1) the client sends `sentAt: Date.now()` beside `budgetMs`; the handler captures `receivedAt` as its **literal first statement** (before the URL parse and `readJson` — both yield points a flush can preempt) and computes `deadlineAt = resolveSearchDeadlineStart(sentAt, receivedAt, budget) + budget`, where the skew guard honors `sentAt` only inside `[receivedAt - budget, receivedAt]` (inclusive) and falls back to `receivedAt` otherwise — additive and back-compatible in both directions, same as `budgetMs`; a queue delay *larger* than one budget falls outside the window by design (untrustworthy as clock evidence), which is acceptable because (3) bounds real delays under one budget. (2) A **pre-flight `overBudget()` gate now precedes the primary FTS scan** — previously the first checkpoint sat after it, so an already-doomed request still paid for the scan; now it returns well-formed `degraded: true` partials in ~ms, and the downstream rescue/vector/coverage checkpoints fall out with no special-casing. The modal surfaces it as "Partial results — indexing in progress, retry in a moment" (`is-degraded` class, `--text-warning`) — distinct from both full results and failure. (3) The flush loop **yields to interactive traffic**: after serving a `/v1/search` mid-flush, the next sub-batch defers up to `INTERACTIVE_YIELD_MS` (1500, per-search and self-decaying), cumulatively capped at `INTERACTIVE_YIELD_CUMULATIVE_CAP_MS` (15s) per flush so continuous searching cannot stall a backfill; a search arriving mid-sub-batch still waits at most that one synchronous transaction — nothing can preempt a `DatabaseSync` statement. And (4) `vectors.invalidate` moved from per-sub-batch to **once per completed flush per touched vault**, inside a `try/finally` so a mid-flush throw still invalidates every vault an earlier sub-batch committed into — trade-off, deliberate: new chunks become vector-searchable at flush end, in exchange for the matrix staying warm during a backfill (it was being rebuilt ~800ms on effectively every mid-backfill search). Both the handler's clock (`now`) and its pause (`delay`) are injectable seams for the real-HTTP tests — keep new timing logic behind them.

- **Companion search latency is governed by how much of the index the query matches, not by index size — so a short query is catastrophically slower than a long one, and the modal's 3-character type-ahead gate is the mitigation.** Measured medians for `/v1/search` against the live index as it stood at measurement time, 52,257 chunks / 5,453 paths (the live index has since been rebuilt smaller — 28,706 chunks / 2,534 paths measured 2026-07-29; the shape of these numbers is what matters, not the absolute index size): `"c"` **733ms**, `"cr"` **239ms**, `"cru"` **27ms**, `"cruc"` **11ms**, `"crucible"` **5ms**, `"orchestration queue"` **2ms**. The shape is not a warm-up artifact — it is the `matched` CTE having to bm25-score every matching chunk before `pooled` collapses it to one row per path, and the trailing term is prefix-expanded (`term*`, the FTS5 `prefix='2 3'` index), so one or two characters match most of the corpus. Hence `SEARCH_TYPEAHEAD_MIN_QUERY_LENGTH = 3` in `src/search/debounce.ts`: below it `VaultSearchModal` does not fire automatically at all, though **Enter still forces any query through** — the gate paces typing, it does not restrict what may be searched. Don't lower it to 2 without re-measuring (2 chars costs ~9x 3 chars). Length is a proxy, not the real variable: a *common* short word stays expensive above the gate (`"the"` **827ms**), which is why `runSearch` also stamps each issue with a `searchGeneration` and discards a response whose generation is stale — with type-ahead, a broad early query outliving a narrow later one is routine, not theoretical, and without the guard the slower, less-specific results land last and win. Sweep mode deliberately opts out of type-ahead entirely (a project brief is not refined keystroke by keystroke, and each sweep costs a query expansion plus a wider result set). Relatedly, `SearchManager` now caches the link-boost graph and drops it from the `metadataCache.on('resolved')` handler in `main.ts` rather than rebuilding per search: `buildLinkGraph` walks all of `resolvedLinks` plus every file's `frontmatterLinks` for ~70ms here — tolerable once per explicit search, but more than the entire companion round-trip for a typical query, and per-keystroke it would be the whole latency budget. `'resolved'` is the correct invalidation event because it is precisely "link resolution has settled after an edit"; a briefly stale graph is harmless because the boost only reorders an existing result set and can never add or remove a result.

- **Obsidian's own "Excluded files" list is honored on both Crucible file surfaces, but asymmetrically on purpose: the search index *hides* those paths, the file-open palette *deranks* them.** `metadataCache.isUserIgnored` (Settings → Files & links → Excluded files) is declared in the `MetadataCache` augmentation in `src/types.ts` and used unguarded — `FileSuggest`/`FolderSuggest` (`src/suggesters.ts`) and `src/folderPicker.ts` have always filtered on it, so before this the palette and search were the two surfaces that silently ignored it. Search now folds it into `SearchManager.isExcludedFromIndex`, the single predicate behind `prepareFile`/`deletePath`/`listIndexableFiles`, alongside `isSearchIndexablePath` and `isPathExcluded(…, 'search')`. The palette instead ORs it into `FileOpenIndex.isIgnoredPath`, which sets `FILE_OPEN_FLAG_IGNORED` and costs the row a flat rank penalty larger than any tier gap — the row stays live and reachable by typing its exact name. That asymmetry is the design, not an oversight: a palette exists to reach a file you can name, whereas a search hit you did not ask for is noise. **Two consequences.** (1) Like `isPathExcluded`, the search filter is **index-time only** — adding a path to either exclusion list stops future indexing but does not retroactively purge rows already in the companion database; run `Orchestrate: Search rebuild index` to drop them. (2) `FileOpenIndex.exclusionSig` must include the raw `userIgnoreFilters` list (read through the presence-guarded, undocumented `vault.getConfig`, per the `src/surround.ts` precedent), because that list is edited inside Obsidian's own settings — no vault event fires and `plugin.settings` never changes, so without it in the fingerprint every IGNORED flag would stay stale until something else invalidated the snapshot. A build lacking `getConfig` degrades to the previous signature rather than throwing.

- **The search companion's vector leg is dimension-agnostic by design, scans the full matrix by requirement, and every number below is measured — don't re-derive them.** `plans/semantic-vector-leg-and-reranker.md` has the full argument; this is the operational summary a future session needs before touching `scripts/search-companion.mjs`'s vector code or `src/search/SearchManager.ts`'s embedding lifecycle.
  - **Dimension-agnostic, and the reason is a settings fact, not a technical one.** `searchEmbeddingModel` is a plain `ProviderModelRef` user setting — Crucible ships publicly, so no model (and no English-only assumption) may be compiled in. The companion therefore stores whatever width arrives (`embedding BLOB` + `embedding_dim INTEGER` + `embedding_model TEXT`, schema v3), records the producing model per chunk, and refuses to silently mix vector spaces inside one vault. **A width conflict at *upsert* time is a 4xx, never a 5xx** — `prepareChunkEmbedding`/`normalizeEmbedding` throw `HttpError(400, …)` on a non-finite/zero/empty/wrong-array embedding, and the vault-wide width check in the `/v1/index/upsert` handler (`refusing a …-dimension vector`) throws 400 specifically because the client (`src/search/client.ts`) turns any 5xx into `SearchServiceUnavailableError` — "the companion is not reachable" — which would send a user to restart a container that is already healthy over what is actually a client-side model-mismatch bug. A width conflict on the *query* side is handled differently and deliberately isn't a 4xx at all: `runVectorLeg` pre-checks the query embedding's width against the scanned space's and, on mismatch, sets `outcome.note` and skips straight to FTS-only (`mode: 'fts'`) rather than failing the whole search — failing a request outright over a mid-model-switch mismatch would be worse than answering with keywords alone.
  - **The scan covers the FULL matrix, never the FTS candidate pool — this is the one mistake that passes every other test.** Reranking FTS candidates by vector similarity cannot surface a note sharing no keywords with the query, which is the entire reason the vector leg exists; a pool-reranking implementation looks correct everywhere else. The named regression test is `tests/searchCompanionVector.test.mjs`'s `'the vector scan covers the FULL matrix, not the FTS candidate pool: a chunk with zero keyword overlap still surfaces'` — it asserts a chunk with zero keyword overlap and a near-identical vector appears in results, with `attribution.textRank === null` and a real `vectorRank`. Do not "optimize" the scan to only touch bm25's candidate set.
  - **The measured numbers** (52,257 chunks, single-threaded JS, `Float32Array` full scan, brute-force cosine — vectors are stored L2-normalised so cosine is a dot product): KNN itself is **13ms at 384d, 24ms at 768d, 33ms at 1024d**, 214MB resident at 1024d. The interactive ceiling this puts on the design is **~250k chunks (~26,000 notes)** — past it, the dependency-free escape hatches are, in order, worker-sharding the scan over a `SharedArrayBuffer` (the matrix is already one flat `Float32Array`) and then `int8` quantization with a float32 rescore of the top ~1000 once residency (not latency) binds. **`int8` is not used today because it measured *slower* in scalar JS** — 19.6ms vs 12.4ms at 384d, no SIMD path to make up the difference — so it's the move for memory pressure, not speed. Separately, the in-memory matrix is dropped on every write and rebuilt lazily on the next vector search (Assumption 8: rebuilt, not patched, because patching can drift and rebuilding can't); that lazy build costs **391ms at 384d, 799ms at 1024d** (reading 52,257 BLOBs + memcpy). Invisible in normal use (one rebuild amortised over many subsequent searches per edit), but during an active backfill every batch *used to* invalidate it, so a search mid-backfill paid **~0.8s at 1024d** — that measurement drove the rsp change (see the sentAt entry below): invalidation now fires once per completed flush, so the matrix stays warm during a backfill and the deferred incremental-append fallback (not built; adding it uninvited would widen the vector backend's seam contract) remains unnecessary at current scale.
  - **The 12-thread ceiling and why `enrich`'s 301 events/s does not transfer.** *(Unverified this run: the 2026-07-25 validity audit found no supporting artifact for these numbers in the archived measurement run — that run measured `bge-m3` only. The figures below are inherited from earlier work; treat them as unaudited legacy data if revisited.)* `bge-small-en-v1.5` measured **3.8 chunks/s at 1 thread, 10.3/s at 4, 20.1/s at 12** (torch's default thread count on this 24-logical/12-physical-core box) — only 5.3× scaling from 1→12, so the box is already near saturation and there is no hidden 12× left to recover by throwing more threads at it. `news-ingestion/enrich`'s frequently-cited "301 events/s" for the same model on the same CPU is **not a contradiction and not transferable** — it's measured over short texts (a title line + a body line), and re-measured against realistic ~1,118-character vault chunks the number is 20.1/s: **15× apart purely on sequence length**. Don't cite `enrich`'s throughput as a projection for anything embedding vault-sized chunks.
  - **The coverage-aware skip, and its three fail-closed rules.** `SearchManager.indexFiles`'s skip condition is `contentHash matches **and** embeddingCoverageSatisfied(stored)` — content hash alone only proves the *text* hasn't changed, not that vectors exist or match the active model, so before this fix flipping `searchSemanticEnabled` on left every already-indexed file permanently vector-less with no error. `embeddingCoverageSatisfied` enforces: (1) **partial coverage is not coverage** — `hasEmbeddings` is `chunkCount > 0 && embeddedCount === chunkCount` server-side (`scripts/search-companion.mjs`'s `/v1/files/state`), so an interrupted backfill's partially-embedded path is correctly re-queued rather than treated as done; (2) **unknown coverage counts as uncovered** — a `hasEmbeddings === undefined` response (an older companion that doesn't report the field) re-indexes rather than skips, because skipping a file that actually needs work is a silent permanent gap while re-indexing a file that didn't need it costs one read; (3) **with semantic off, coverage leaves the skip condition entirely** — `activeEmbeddingModelId()` returns `null` when `searchSemanticEnabled` is false or no model is picked, and `embeddingCoverageSatisfied` short-circuits to `true` in that case, so an FTS-only vault skips exactly as it always did rather than every file looking permanently stale and re-upserting itself every pass.
  - **`SCHEMA_VERSION` and `SEARCH_REQUIRED_SCHEMA_VERSION` are bumped together (per the pairing rule at the top of this file — they were 3 when embedding storage landed and are **7** today), and the FTS migration is independent of that bump.** `migrateFtsSchema` (`scripts/search-companion.mjs`) keys on whether `chunks_fts`'s stored SQL already contains `prefix=`, not on `SCHEMA_VERSION` — so the 2→3 embedding-storage bump did **not** trigger an FTS drop/refill; only the earlier 1→2 `prefix='2 3'` change did, and would again on a hypothetical schema-1 database. The 2→3 migration itself is additive `ALTER TABLE chunks ADD COLUMN` statements (`embedding BLOB`, `embedding_dim INTEGER`, `embedding_model TEXT`; schema 4 added `embedding_space TEXT` the same way) — no drop/refill of `chunks`, and nothing to backfill on upgrade since `searchSemanticEnabled` has always defaulted false (zero embeddings existed anywhere before this landed). The legacy `embedding_json` column from schema 1/2 is deliberately left in place on a migrated database rather than dropped — it's never read or written again and dropping it would mean a table rebuild for nothing.
  - **The vector backend is a narrow, injectable seam on purpose — `{ name, stats(vaultId?, space?), knn(vaultId, queryVector, k, space?), invalidate(vaultId?) }` — and nothing outside `createVectorBackend` may assume a flat array or an in-process scan.** (The two `space?` parameters arrived with schema 4's embedding-space filter; both are optional and additive, so a backend stub that ignores them still satisfies the seam — `resolveScanSpace` treats a backend reporting no spaces as single-space. `statsCache`/`matrixCache` are correspondingly two-level, vault → space → value, with `null` as the "all vaults" / "no filter" key, and `invalidate(vaultId)` drops the vault's whole inner map rather than one key.) That's what makes the two documented escape hatches (a `vec0`/sqlite-vec backend, a worker-sharded backend) a swap of this factory rather than a rewrite of `runSearch`/`fuseSearchRows`. The factory lives in `scripts/search-companion/vectors.mjs` (rem-R3; re-exported through the facade, so existing imports are unchanged). The Dockerfile `COPY`s the facade plus the `scripts/search-companion/` directory — a new script file *outside* that directory still silently breaks the container image build and needs its own Dockerfile change in the same commit.

- **A chunk id is unique only *within* a vault — every companion statement keys on `(vault_id, id)`, and one that keys on `id` alone is a data-loss bug, not a style nit.** `stableChunkId` (`src/search/chunker.ts`) derives an id from the note's path, ordinal and heading, so two vaults holding the same note at the same path minted the *same* id. The companion's `chunks` table was `PRIMARY KEY (id)` and the upsert conflicted on `id` alone with `vault_id = excluded.vault_id` in its SET list, so indexing vault B silently **re-labelled vault A's row as B's**: A's file then vanished from A's own (correctly vault-scoped) `/v1/files/state`, A's search stopped returning it, and a `/v1/index/reset` of *B* deleted A's data along with B's. Reproduced against an in-memory database running the real `createSchema` + `createRequestHandler`, not inferred. It was silent and partially self-healing, which is worse: A's next sweep saw the path missing, re-chunked it and stole the row back, so two vaults on a timer ping-pong the same rows forever, each intermittently missing the colliding notes, with no error anywhere. `docs/search-companion.md` had specified `vaultId + chunkId` keying the whole time — a user following the documented "multiple vaults can share one companion database" landed straight in it. The fix is both halves: `stableChunkId` folds `vaultId` into its hash (readable prefix unchanged — the id is still `path#ordinal:hash`), and schema **5** rebuilds `chunks` with `PRIMARY KEY (vault_id, id)`. **Do not reintroduce an `id`-only chunk statement** — the four that were wrong are the upsert's conflict target, the `chunks_fts` delete, `HYDRATE_CHUNK_SQL` (an id-only hydrate is a cross-vault *content leak*, not just a wrong snippet), and the FTS→`chunks` join; the last two were safe only because ids happened to be globally unique. `tests/searchVaultIsolation.test.mjs` is the barrier, and it is the first test in the suite to write two distinct `vaultId`s into one database — every other companion test pins a single constant, which is exactly why nothing caught this. Three notes on the migration (`migrateChunksPrimaryKey`): (1) it is a **lossless table rebuild, not a reindex** — SQLite cannot `ALTER` a primary key, so it creates the replacement, `INSERT ... SELECT`s every column plus the `rowid` across, drops, renames, then drops and refills `chunks_fts` in the same transaction (the `migrateFtsSchema` precedent); embeddings ride across untouched and nothing re-embeds. (2) The copy **cannot** lose a row, and the proof is from the old constraint rather than from the data: `id` unique across the whole database implies `(vault_id, id)` unique. Measured 2.7s over a synthetic 52,257-chunk / 1024d index. (3) It carries forward any column the current shape no longer declares (today only the vestigial `embedding_json`) rather than dropping it, and the reads happen *after* the additive `ALTER`s, so a schema-1 database migrates in one startup. Per the pairing rule, `SEARCH_REQUIRED_SCHEMA_VERSION` moved to 5 too — so between a plugin update and a container rebuild, health reports `ok: false` and search is **unavailable, not degraded**. Rebuild the companion image in the same landing.

- **`embedding_space` (schema 4) is a conservative guard, NOT evidence that precision changes the vector space — the measurement that justified it did not reproduce, and the corrected result is that engine, build and precision are all retrieval-irrelevant.** The superseded claim (recorded here until 2026-07-25, and still worth knowing because it is a textbook statistical trap) was: from an unseeded 150-chunk sample with 11 queries, runtime-only agreement was perfect while precision-only fell to top-10 Jaccard **0.8182**, i.e. "one result in ten changes place" — and that asymmetry is why the space key is `modelId + '/' + normalizedPrecision`. Re-measured over 300 stratified chunks and **60** queries with all runtimes embedding byte-identical texts in one pass (archived as `measurements/esi-fr-2026-07-25/` in the eval-harness repo): **every** pair — runtime-only, precision-only, and build-only — reads mean Jaccard 0.9939 / min 0.8182. Nothing separates. The control that settles it is build-only: `crucible-embed-gpu` mounts `~/.lmstudio/models` read-only and loads a file whose **sha256 is identical** to the one LM Studio serves, so weights, precision and architecture are all pinned and only the llama.cpp build varies — and it churns exactly as much as the precision arm. **Two statistical traps, and they are mirror images.** (1) `0.8182` is exactly **9/11** — the smallest non-trivial disagreement Jaccard@10 can express. At 8 queries it appeared to partition the runtimes perfectly; at 60 every pair reaches it. **The min is a floor, not a discriminator**, and it converges to that floor for everything as n grows. (2) The earlier lesson "report the min, never the mean" was therefore itself too narrow: a mean hides a difference that exists, a min hides one that does not. Report enough of the distribution to tell a floor from a signal, and treat **n ≥ 50 queries** as the minimum for any rank-overlap arm here. Ground-truth quality measurement (`scripts/embedding-quality.mjs`) then closed it: across two engines, two llama.cpp builds, two GGUF conversions and the quantization ladder down to Q8_0, cross-lingual retrieval P@1 and discrimination spread are **identical to four decimal places** — the churn is real and has no quality consequence. So: keep the mechanism (it fails closed, costs nothing when precision is unreported, and prevents genuinely incompatible spaces sharing a matrix), but do **not** cite it as proof that f16 and fp32 differ, and note it cannot see the failures that actually destroy retrieval — a cross-encoder at the same width and precision is the *same* `embedding_space` by this definition. The plumbing itself is unchanged and still correct: coverage compares the space not the model id, the vault-wide upsert guard is width-**and**-space (4xx, never 5xx), the vector scan filters by it, precision is *probed* (`describeModel`) rather than parsed from the model id (LM Studio registers one model under ~8 aliases, some carrying the quant and some not), `normalizePrecision` collapses `Q4_K_M`/`q4_k_m`/GGUF `file_type: 15` to one token, and an unreported precision degrades to the bare model id — which is what made the migration free, since Infinity exposes no dtype at all.

- **Quantization degrades *spread*, not *ranking* — the "embedding models lose more to quantization than chat models" assumption is not supported here, and Q2_K still retrieves perfectly.** The plan's Decision 2 chose f16 over Q8_0/Q4_K_M on that assumption and explicitly recorded Q4 as *assumed* to diverge rather than tested. Measured against ground truth (61 parallel Wikipedia articles, en/fr/ja, 11 topic clusters — `scripts/embedding-quality.mjs`, `npm run search:quality`, dataset frozen at `measurements/esi-fr-2026-07-25/samples/S5-wikipedia.json` in the eval-harness repo): fp32, f16 (two independent conversions) and Q8_0 are **indistinguishable** (en→fr P@1 100%, en→ja 98.4%, spread 0.3513–0.3516); **Q4_K_M** costs exactly one article out of 61; **Q2_K at 366 MB scores 100%/100%**, the best alignment in the table. What quantization actually does is compress the space — Q2_K's unrelated-pair similarity rises 0.4416 → 0.5882, cutting spread to 0.2383 — and since retrieval reads *order*, retrieval survives while anything reading *absolute scores* does not. Two consequences worth keeping: **(a)** the margin `min(translation cosine) − max(cross-cluster cosine)` is **negative in every configuration measured, including those at 100% P@1**, so no global similarity threshold separates a true match from a stranger — rank results, never write `score > 0.5`; **(b)** the real quality risks are model-shaped, not precision-shaped — a cross-encoder used as an embedder (P@1 19.7%, spread 0.0087, ordering inverted) or a model that does not cover your languages (`nomic-embed-text` measures 85.2% on en→ja with a 3.3× narrower spread). When adding a quality claim here, use the translation trick: an article and its translation share almost no vocabulary, so only a model that encoded meaning ranks them together, and no human judgment is needed.

- **FTS5's implicit AND is per *chunk*, not per document — that is the root cause of the "matt pocock" class of misses, and the fix is a separate coverage retrieval leg, not a looser MATCH.** A note whose query terms are all present but split across two of its own chunks can never satisfy the strict AND (no single chunk has them all), while an unrelated note that name-drops every term in one throwaway paragraph does — and because the decoy produces *some* hit vault-wide, the zero-hit loose-OR rescue never fires (starved at ~5.4k notes). The fix landed as `rankingMode` on `POST /v1/search` (`'current'|'blend'|'coverage'|'blend+coverage'`; unknown → HTTP 400, never a silent degrade): `coverage` runs one presence-only `COVERAGE_SQL` MATCH per query term (structurally the vector leg's twin — a separate retrieval leg with hydration at the best-covering chunk, `score_text: null`, fused as a fourth RRF rank), inert below `COVERAGE_MIN_TERMS = 2`. **It is a leg, not a pool rerank, on purpose:** a rerank over the strict-AND pool can never rescue a target the pool never contained — a pool-only implementation looks correct everywhere except on the exact bug it was built for (the same trap as the vector leg's full-matrix rule). **The default is `'coverage'`, by measurement** (eval-harness `measurements/fsq-bakeoff-2026-07-26/`, 46 graded queries on a copy of the live index): the only mode improving every metric with zero rank-1 losses — MRR +15%, R@25 +26%, sign test p = 0.00052, +3–14ms p50 at 1–4 terms; the entire win is the split-terms family (R@25 0.42 → 0.92). **Do not promote `blend` to default** — measured net-negative alone (MRR −13%, every severe rank-1 displacement in the sweep, 5.4x latency at 5–8 terms); it stays a per-request option. Two measured follow-up levers, cheap and independent: (a) the coverage leg's tie-break is score-desc-then-*path-ascending* before truncation to `poolSize` — on a 2-term query 415 paths tied at 1.0 and the target sat at alphabetical index 344, discarded before fusion ever saw it; break ties on the covering chunk's bm25 or per-path chunk-coverage count instead. (b) `poolSize = max(limit*4, 40)` gates the leg by the *display* limit — the same 12 shown rows score MRR 0.474 searched at limit 12 vs 0.504 searched at limit 25 then truncated; `COVERAGE_SQL` takes no LIMIT, so a pool floor independent of `limit` is nearly free. The 9+ term natural-language shape is the leg's real cost (+580ms — up to `MAX_QUERY_TERMS = 24` FTS scans); the flagged mitigation is capping terms scanned, rarest-first, never truncating a single term's path list.

- **The entity facet (schema 7): frontmatter `author` reaches FTS as a dedicated `entities` column on *every* chunk, and `contentHash` folds the emitted entity text — both halves are load-bearing.** One mechanism, two sources by design: an entity is `{text, type, source: 'frontmatter'|'model'}` (`SearchEntity` in `src/search/types.ts`) so GLiNER2 body-text spans later arrive as a producer change, not a schema bump — the companion flattens to text (`normalizeChunkEntities`) into one untyped column at bm25 weight **8.0**, deliberately *below* title's 10.0 (a tiny field already bm25-scores high before weighting; an over-weighted author turns every common first name into that author's back catalogue — raise it only against a measurement, the bake-off did not cover this column). Every-chunk emission is the ranking decision, not convenience: per-chunk AND means an entity on chunk 0 alone could never co-occur with a body term in chunk 4 — the exact split-terms failure again; per-path pooling collapses the duplication. The flattening rule exists **twice** (`entityIndexText` in `chunker.ts`, `normalizeChunkEntities` in the companion — no shared module crosses that boundary) and their exact agreement is asserted by test; if they diverge, the client's `contentHash` describes text the index does not hold. The fold itself is not redundant with hashing raw content: it survives a future narrowing of the hash to the note body, and it covers extraction-rule changes (a new `FRONTMATTER_ENTITY_FIELDS` row) that change entity text under byte-identical content. **Consequence at any change to either:** every note's hash moves and the next sweep re-upserts (and with semantic on, re-embeds) the whole vault — that is the population mechanism, not a bug. `attribution.entityTerms` (whole-word-or-prefix, `[]` distinct from omitted) stops at the companion boundary today: `client.ts`'s `normalizeAttribution` whitelists keys, same as the coverage keys. A malformed entity is dropped at upsert, never a 400 — junk frontmatter costs the note its facet, not its indexing.

- **The search query log lives in the plugin data dir (`.obsidian/plugins/<id>/search-query-log.json`), outside the vault's note tree, so it cannot be indexed by construction** — not by an exclusion setting a user could later edit; that closes the "the log becomes searchable and pollutes its own measurements" loop outright. `src/search/queryLog.ts` is the store (bounded, oldest-first eviction, promise-chain-serialized writes; every mutator is fire-and-forget and non-throwing — a measurement side-channel must add neither latency nor a failure mode to the interactive search path). The export (`Search: export query log`) deliberately **omits and counts** click-less queries rather than emitting them with empty `targetPaths`: every IR metric scores an empty-target row as a miss, which would be abandoned-search inference smuggled in through the export — the no-abandonment rule is a data-shape constraint, not a UI nicety.

- **Linked-post chunks (pf-3): a source note ranks on the text of the `x-metadata`/`yt-metadata` notes it stamp-links — as ordinary chunks, with NO schema bump and NO companion change.** `SearchManager.resolveLinkedDocuments` reads the stamps off the frontmatter cache (cap 8 targets, first-listed wins, applied to the raw stamp list *before* resolution so the cap is deterministic), resolves via `getFirstLinkpathDest`, `cachedRead`s each target, strips frontmatter (`stripFrontmatterBlock`, exported from the chunker), trims/caps at 4000 chars, and hands `{path, title, text}[]` into `buildSearchChunks` — which emits one ordinary chunk per entry (heading `Linked post: <title>`) carrying the **citing** note's path/title, exactly as image-description chunks carry the embedding note's identity. Ordinary chunks are the whole design: FTS, coverage, and the vector leg pick them up with zero companion involvement, which is what makes a semantic query over a post's text return the thread that only links it. Invalidation rides the existing `extraHashFacets` seam on `hashSearchContent` (`linked:<path>:<hash>` per surviving target, composed with the image facets in `prepareFile`): an unstamped note hashes byte-identically to pre-pf-3 (no vault-wide re-upsert wave), a stamp arriving moves the hash once, and a linked target's *text* changing re-upserts the citing note even though the citing note's own bytes never moved. X tombstones (frontmatter-only, empty body) contribute neither chunk nor facet — a dead post can never move a thread's hash. The chunker stays pure (assembly lives in `SearchManager`; `parseSearchDocument` untouched). Companion piece, pf-4: `buildLinkGraph` also records a directed `citedBy` index in the same walk, `SearchManager.citersOf(path)` reads it off the cached graph (never a per-result scan), and `SearchModal` renders a muted "cited by" line (cap 3, `+N more`) on results under a configured metadata root — citer clicks deliberately bypass `recordOpen` (the query log grades ranked picks only), and `applyLinkBoost` is regression-pinned byte-identical.

- **Superseded interactive searches are recallable end to end (ss-1/ss-2): the client aborts them on the wire, the companion abandons them pre-flight, and the deadline skew guard no longer rewards long queuing with a fresh budget.** The type-ahead's 200ms reset-debounce fires one query per typing *pause*, and pre-ss each one was unrecallable — `requestUrl` cannot abort, so superseded/timed-out searches ran to completion on the companion's single synchronous thread, forming the invisible queue behind live queries. Client half (ss-1): interactive `/v1/search` only rides `fetch` + `AbortController` (`fetchSearch` in `client.ts`; a scoped `eslint-disable` covers the plugin lint rule banning bare `fetch` — `requestUrl` has no abort story, which is the whole point), with a session-latched `requestUrl` fallback on a CORS/network-shaped `TypeError`; the modal holds one live controller and aborts at every `searchGeneration` bump; the client timeout aborts rather than abandons; `SearchAbortedError` is deliberately NOT a `SearchServiceUnavailableError`, so an abort can never trip the availability latch or a failure counter, and never surfaces a Notice. Companion half (ss-2): the body carries optional `clientId`/`seq` — attached **only when the caller passed a `signal`** (the modal), never the background sweep, so a workflow query can neither supersede nor be superseded by a typing session; `searchClients.mjs` is a bounded LRU high-water tracker consulted at the same pre-flight spot as `overBudget()`, answering `degraded+superseded` before any SQL; identity-less requests are byte-identical to before. Two traps this work codified: (1) **`req.destroyed` is NOT a disconnect signal** — Node auto-destroys an `IncomingMessage` shortly after its body finishes streaming, so gating on it silently drops every real request behind a timing race (confirmed live: `/v1/search` hung forever); the correct signal is `res.on('close')` *registered before `readJson`*, which fires only on genuine premature teardown. (2) The skew guard's past-trust window is `SEARCH_DEADLINE_SKEW_TRUST_BUDGETS = 5` budgets, not 1 — at 1, a queue delay over one budget made the guard distrust `sentAt` and restart from `receivedAt`, granting a full fresh budget to exactly the requests queued longest (the one-budget bound was only ever justified by the *upsert* flush loop's yield; searches have no such yield between them).

- **Companion code ships only via an image rebuild — `home-compose up crucible-search` — because the container bakes `scripts/` into the image; a bare `docker restart crucible-search` runs stale code.** The `crucible-search` service (context-control `compose.home.yml`, build context = this repo, `CRUCIBLE_GIT_SHA` baked as an OCI revision label for Command Center's commits-behind view) mounts only the `/data` volume. `home-compose up` is `docker compose up -d --build`, so it is the restart command *and* the deploy command in one. Consequence for any landing that touches `scripts/search-companion*`: the running companion does not have the change until that rebuild runs — say so in the landing/validation notes, the same way a schema bump already demands "rebuild the companion image in the same landing."

- **`POST /v1/paths` (sa-1, additive — no schema bump) is the enumeration endpoint the audit pair depends on, and the audit/reconcile split is a hard read/write boundary.** Before it, nothing could ask the companion "what paths do you hold?" (`/v1/files/state` only echoes paths the caller names), so orphan detection — chunks left behind by offline deletions, moves, or exclusion changes, which no vault event will ever purge — was structurally impossible client-side. The endpoint returns every indexed path for a vault (`{path, mtime, contentHash, chunkCount, embeddedCount}` + `totals`) from ONE aggregate query: `selectPathsByVault` generalizes `selectStateByPath`'s dominant-content-hash-group rule to all paths via `ROW_NUMBER() OVER (PARTITION BY path ORDER BY COUNT(*) DESC)` — a mid-rewrite path's minority-hash stragglers are invisible here exactly as they are to `/v1/files/state`, transient and self-healing, not a gap the client must handle. Client side (sa-2): **`Search: audit index` is read-only by contract** — it compares `listIndexableFiles()` vs `/v1/paths` vs the image-description store (missing / orphans / stale-by-mtime / embedding gaps / image coverage incl. the durable `kind:'failed'` count) and writes only its overwrite-per-run report note (`_crucible/search-audit.md`) — it must never enqueue, delete, or touch the index. **`Search: reconcile index` is the only mutating half and mutates only by enqueueing existing job types** (`search_upsert_file` for missing+stale, `search_delete_path` for orphans — payload `{path}`, mirroring `SearchIndexCoordinator.enqueueAutomatic`), with the orphan-deletion half routed through `confirmDestructive('search-reconcile-orphans', …)`. Two pure-compute rules pinned by test (`src/search/audit.ts` — dependency-free, rem-R4): `embeddingGaps` is gated on `searchSemanticEnabled` (an FTS-only vault would otherwise report every path as a permanent fake gap), and an mtime false-positive is harmless by design — the enqueued upsert no-ops on content-hash match. The widened `/health` passthrough (`normalizeHealth` now carries embeddedChunks/model/dim/spaces) is what makes a mixed `embeddingSpaces` index *visible* — the settings Companion status panel and `search-health` both flag it.

- **The tag boost (WP-TB2, `src/search/tagBoost.ts`) is client-side and frontmatter-only, keyword-dump queries are a structural non-goal for it, and rerank stays a manual action.** The measured record is eval-harness `local-inference-bench/measurements/tag-boost-arm-2026-08-01/` (TB1): a flat additive `score += weight` on `metadata.tags ∋` a configured tag, at weight **0.005**, rescued the RC sentence-form queries to rank 1 with **zero regressions** across the 52-query corpus, so that is the shipped default (`searchTagBoost{Enabled,Tags,Weight}`, default off / `["gold"]` / 0.005; applied inside `boostSearchResponse` independently of the link boost, recorded as `attribution.boosts.tag`). Four boundaries that must not blur. (1) **Frontmatter tags only** — the companion indexes the note's frontmatter `tags`; an inline body `#gold` is invisible to the boost, by construction, not by bug. (2) **A client-side boost can only reorder what the client fetched**: the RC2 keyword-dump query's target is absent from the pool even at limit 200 (5× the live fetch), so no client-side lever — tag boost, months boost, or rerank — can ever surface it. Rescuing keyword-dump queries needs the server-side post-fusion pre-truncation hook (`ranking.mjs`, after fusion, before `slice(0, limit)`), a documented follow-up, not a tuning problem. (3) **Weight is calibrated to the fused-score scale** (top-10 spreads ~0.010–0.023, adjacent gaps ~0.0002–0.009): 0.02 buys full RC4 rescue but demotes a true target whenever another tagged note sits within the weight of it (measured: 2 regressions), and 0.1 is strictly worse — don't raise the default without re-running the arm. (4) **Rerank remains a deliberate manual action** — TB1's rerank-replica arm fed the cross-encoder the exact live `rerankDocumentText` shape and still measured rerank net-negative for sentence-keyword queries (RC3 3→30) while decisive for linked-post queries, closing v3's open Finding 3 (wrong-document-text ruled out; the live "reranker saved it" observation most plausibly reflects pool composition). Any auto-rerank default would need a query-shape gate that deliberately does not exist.
