# src/providers/ — model provider clients

Local instructions for the provider seam (`ollama.ts`, `openaiCompatible.ts`, `shared.ts`, …)
and its consumers in `src/providers.ts` / `src/agents.ts` / `src/modelPicker.ts`. The root
`AGENTS.md` is the canonical contract; this file adds what is only true here.

Related areas: the container that serves these endpoints locally is
`/home/_shared_code/inference-engine/llama/AGENTS.md` (inference-engine repo); the embedding-model lifecycle that consumes them is
`src/search/AGENTS.md`; the user-facing writeup is `docs/local-inference.md`.

## Quirks index

The one-line hooks below say *where to walk*, not what to do — read the full entry before acting.

- LM Studio (and llama.cpp/vLLM/LocalAI) is the `openai-compatible` provider kind, not `ollama`.
- Completion-class calls ride a per-provider concurrency limiter — release on settle, local default 1, embed/rerank exempt.
- A reranker is not an embedding model — every structural guard passes it.
- Every LLM completion call sends `max_tokens` — an uncapped request can generate to the context ceiling.
- `src/providerModelContract.ts` is the single model-ref/binding parser and stays a dependency-free leaf.

## Quirks

- **LM Studio (and llama.cpp/vLLM/LocalAI) is the `openai-compatible` provider kind, NOT `ollama`.** The two local kinds speak different wire protocols: `ollamaClient` (`src/providers/ollama.ts`) POSTs to `<baseUrl>/api/chat` with Ollama-native JSON, while LM Studio serves the OpenAI wire format at `<baseUrl>/chat/completions`. Pointing an `ollama`-kind provider at LM Studio's port silently fails — LM Studio doesn't serve `/api/chat`, so the response carries no `message.content`/`done_reason`, the client yields empty text + `rawFinishReason: undefined` → normalized `'unknown'`, and the strict `enforceNormalFinishReason` guard (`src/agents.ts`) throws `finished with non-normal reason "missing" (normalized: unknown; partial response length: 0)`. Two non-obvious things about the `openai-compatible` kind: (1) **`baseUrl` must include the API path** — `openAICompatibleClient` builds `${apiBaseUrl(provider)}/chat/completions` and `${apiBaseUrl(provider)}/embeddings`, so the Server URL field expects e.g. `http://localhost:1234/v1`, not the bare host:port. (2) **The API key is optional** — `httpContext` (`src/providers.ts`) skips the missing-key throw for `openai-compatible` (as it does for `ollama`), and `authHeaders` only emits `Authorization` when a key is present, so a no-auth local server works while a vLLM `--api-key` server can still carry one. The same `openAICompatibleClient.complete()` now resolves its URL through `apiBaseUrl()` for all three kinds (`openai`/`openrouter`/`openai-compatible`); the vendor kinds are behavior-preserving because `apiBaseUrl` falls back to their fixed defaults when `baseUrl` is empty. Temperature is pinned (`0.7`) only for the `openai` vendor — OpenRouter and local servers leave it to the model default.

- **Every completion-class request routes through `ProviderManager`'s per-provider concurrency limiter, and the slot releases when the underlying call SETTLES — never when a caller's timeout race abandons it.** The rsp sprint's image-batch "timeouts" were self-inflicted concurrency: 5 in-flight vision calls against a 4-slot single-GPU llama-server pushed per-request wall time from 6.3s (solo) to ~30s average, and all 7 "timeout" failures had actually completed HTTP 200 at 121–136s — 2–16s after the plugin's 120s `withTimeout` gave up (`runs/dispatch/feedback-image-timeout-investigation.md`; the router log shows only *completed* requests, so an in-flight runaway is invisible and "the router looks idle" proves nothing). The limiter (`ProviderConcurrencyLimiter` in `src/providers.ts`) is a FIFO hand-off semaphore keyed by provider id, wrapped around exactly three `ProviderManager` methods — `complete()` (CLI and HTTP branches both), `describeImage()`, `extractImageMetadata()` — which is the entire completion-class surface, structurally: nothing outside `providers.ts` holds a provider client reference. `embed()` and the native `rerank()` path are exempt **by construction** (the limiter call is simply absent — a different model/latency class; serializing a search embed behind a 2-minute vision pass would be a regression), while the rerank *fallback* path calls `this.complete()` and correctly inherits the limit. Three rules that keep it sound: (1) **release-on-settle** — the limiter wraps the closure around the actual client call, so a `withTimeout` race abandoning the outer promise does not free the slot; `requestUrl` is not abortable, the request is still occupying the GPU, and releasing early re-creates the measured pile-up amplifier through the limiter itself. (2) The default resolves via the **exported `isLocal`** from `openaiCompatible.ts` (the same detection that gates `reasoning_effort` — never a second heuristic): `openai-compatible` → **1**, everything else (cloud kinds AND CLI kinds, which run their own subprocess) → unlimited. `Provider.maxConcurrentRequests` (settings UI: provider editor → "Max concurrent requests") overrides with any positive integer. (3) `image_metadata_extract` is a **retired job type** — `ProviderManager.extractImageMetadata()` has zero live callers (the `imageMetadataExtraction*` settings keys are legacy naming for the current image-describe config); it is wrapped anyway so any future caller inherits the limit. Related, same sprint: `transcodeToPngDownscaled` in `src/orchestration/utils/imageDescribe.ts` caps the vision transcode long edge at 1568px (shrink-only) — it deliberately duplicates ~10 lines of `src/search/imageTranscode.ts`'s canvas shape rather than parameterizing the shared function; unifying them is fine but touches the search area's file.

- **A reranker is not an embedding model, and every structural guard passes it — the trap is the *endpoint*, not the model.** LM Studio serves cross-encoder rerankers through `/v1/embeddings` and lists them as `type: embeddings`; `text-embedding-bge-reranker-v2-m3` returns **1024d at L2-norm 1.000000** (exactly `bge-m3`'s width) and `text-embedding-bge-reranker-base` returns **768d** (exactly `nomic-embed-text`'s). Width matches, the vector is already normalised, the id begins `text-embedding-`, and the server itself reports it as an embedding model — so nothing errors, anywhere, ever. Measured against ground truth over 61 parallel Wikipedia articles in en/fr/ja (`npm run search:quality`): cross-lingual retrieval P@1 collapses to **19.7% (en→fr) / 13.1% (en→ja)** against **100% / 98.4%** for the same model family used correctly, discrimination spread is **0.0087 versus 0.3513** — a factor of **40** — every similarity it returns lands in a 0.92–0.94 band whatever you feed it, the worst true translation ranks **61st of 61**, and the ordering is **inverted**: unrelated same-topic documents outscore a document's own translation. (The earlier figure quoted here, margin 0.0080 vs 0.3994 from one query against four documents, was directionally right and is superseded by the above.) The same weights rank correctly through a real `/rerank`: a cross-encoder scores a *(query, document)* pair jointly and has no meaningful standalone vector, so pooling its internals into 1024 floats produces a well-formed number that means nothing. Structural mitigation is the **Rerank** model capability (keeps it out of the embedding picker); `looksLikeCrossEncoder`/`warnIfCrossEncoderEmbedder` (`src/providers/shared.ts`) additionally warn, session-deduped, when an id or reported `arch` matches `/rerank|cross-enc/i` — deliberately a **warn, never a block**, because no field in any local runtime's API structurally distinguishes cross-encoder from bi-encoder, so a naming heuristic is the only signal available and a false positive must not stop indexing. Rerankers only work through a server exposing a real rerank endpoint: **Infinity is not the only one** — `llama-server` has had `--reranking --pooling rank` all along and ships inside LM Studio's own backends, which the earlier "Infinity is the only local reranker" conclusion missed by checking LM Studio's *server* and stopping. Wire-contract difference between them: llama.cpp returns **raw logits** (negative, unbounded — `+1.66` / `−11.03`), Infinity returns **sigmoid-normalised 0–1** (`0.6047`). Higher is better in both so ordering and the strict parser are safe, but any UI, test or threshold asserting a 0–1 range is wrong against llama.cpp, and rerank scores are not comparable across servers. User-facing writeup: `docs/local-inference.md`.

- **Every LLM completion call must send `max_tokens` — an uncapped request is `n_predict: -1` on llama-server, and a temperature-0 repetition loop will generate until the context ceiling.** The first live image-descriptions batch hit this twice in 100 images: `describeImagePass` sent no cap, so a dense chart at `temperature: 0` looped for ~10 minutes at 97% GPU (`extraction=597888ms`) until the model's 32k context filled, storing 94k/76k-char degenerate coordinate dumps that were then indexed into notes — while the batch appeared silently stalled (no timeout existed anywhere in the path, and `requestUrl` is not abortable). The hardening (`plans/image-describe-hardening-ux.md` WP-1) has four layers, and each is load-bearing: (1) per-pass caps sent **unconditionally** — `IMAGE_DESCRIPTION_NARRATIVE_MAX_TOKENS` 512 / `IMAGE_DESCRIPTION_EXTRACTION_MAX_TOKENS` 2048 in `src/providers/shared.ts`; `max_tokens` is universal on chat/completions, so unlike `reasoning_effort` it takes no `isLocal` gate; (2) `withTimeout` (`src/orchestration/utils/imageDescribe.ts`) bounds every provider pass (120s) and transcode (30s) — since the request can't be aborted, the race abandons the promise and the server-side cap bounds the rest; (3) a per-image try/catch writes a durable `kind: 'failed'` store record: `has()` staying true for it is the point (poison images are skipped on later runs, not retried forever), but failed records must emit **no chunks and no facet** — `resolveImageDescriptions` filters them explicitly so a failure's arrival never moves a note's `contentHash`; (4) the backfill self-heals pre-cap damage via `pruneDegenerate(20_000)` (healthy extraction: median ~1.3k chars, max ~7.4k — the 20k threshold is far from both) so degenerate vision records fall out of `has()` and re-describe under the caps. The generalizable rule: a bounded `max_tokens` is part of the request contract for any new completion call in this plugin, not a tuning knob — and "the router looks idle" proves nothing, because llama-swap logs only completed requests while an in-flight runaway is invisible.

- **`src/providerModelContract.ts` is the single provider/model-ref + agent-binding contract, and it must stay a dependency-free leaf (rem-R2).** Three copies of the `"providerId:modelId"` parser existed because the canonical one was private to `agents.ts` — the third hid inside `ai.ts`'s constrained-allowlist dropdown and was only found by sweeping for first-`:`-split logic, not by grepping a function name. Everything now imports the leaf: `parseModelRef` (first-separator split; `null` for anything incomplete), `formatModelRef`, `modelRefEquals`, `bindingForMode` (the ONLY thing a mode-change handler assigns), `bindingModelRefs`, and `normalizeAgentBinding` — which, called from `main.ts`'s `migrateSettings`, is the only place persisted binding JSON crosses into the `AgentModelBinding` union. Two distinctions that must not blur: the union guarantees payload *structure*, not *completeness* — a half-configured pinned ref is legal state, and `isCompleteModelRef` is the separate runtime question; and leaf-ness is pinned by an esbuild-metafile test in `tests/providerRefs.test.mjs`, so don't add imports to the module. One deliberate behavior change shipped with it: switching a binding Pinned→Constrained→Pinned no longer resurrects the old pinned ref (`bindingForMode` drops the previous payload by design).
