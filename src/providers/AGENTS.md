# src/providers/ — model provider clients

Local instructions for the provider seam (`ollama.ts`, `openaiCompatible.ts`, `shared.ts`, …)
and its consumers in `src/providers.ts` / `src/agents.ts` / `src/modelPicker.ts`. The root
`AGENTS.md` is the canonical contract; this file adds what is only true here.

Related areas: the container that serves these endpoints locally is
`docker/llamacpp-vulkan/AGENTS.md`; the embedding-model lifecycle that consumes them is
`src/search/AGENTS.md`; the user-facing writeup is `docs/local-inference.md`.

## Quirks

- **LM Studio (and llama.cpp/vLLM/LocalAI) is the `openai-compatible` provider kind, NOT `ollama`.** The two local kinds speak different wire protocols: `ollamaClient` (`src/providers/ollama.ts`) POSTs to `<baseUrl>/api/chat` with Ollama-native JSON, while LM Studio serves the OpenAI wire format at `<baseUrl>/chat/completions`. Pointing an `ollama`-kind provider at LM Studio's port silently fails — LM Studio doesn't serve `/api/chat`, so the response carries no `message.content`/`done_reason`, the client yields empty text + `rawFinishReason: undefined` → normalized `'unknown'`, and the strict `enforceNormalFinishReason` guard (`src/agents.ts`) throws `finished with non-normal reason "missing" (normalized: unknown; partial response length: 0)`. Two non-obvious things about the `openai-compatible` kind: (1) **`baseUrl` must include the API path** — `openAICompatibleClient` builds `${apiBaseUrl(provider)}/chat/completions` and `${apiBaseUrl(provider)}/embeddings`, so the Server URL field expects e.g. `http://localhost:1234/v1`, not the bare host:port. (2) **The API key is optional** — `httpContext` (`src/providers.ts`) skips the missing-key throw for `openai-compatible` (as it does for `ollama`), and `authHeaders` only emits `Authorization` when a key is present, so a no-auth local server works while a vLLM `--api-key` server can still carry one. The same `openAICompatibleClient.complete()` now resolves its URL through `apiBaseUrl()` for all three kinds (`openai`/`openrouter`/`openai-compatible`); the vendor kinds are behavior-preserving because `apiBaseUrl` falls back to their fixed defaults when `baseUrl` is empty. Temperature is pinned (`0.7`) only for the `openai` vendor — OpenRouter and local servers leave it to the model default.

- **A reranker is not an embedding model, and every structural guard passes it — the trap is the *endpoint*, not the model.** LM Studio serves cross-encoder rerankers through `/v1/embeddings` and lists them as `type: embeddings`; `text-embedding-bge-reranker-v2-m3` returns **1024d at L2-norm 1.000000** (exactly `bge-m3`'s width) and `text-embedding-bge-reranker-base` returns **768d** (exactly `nomic-embed-text`'s). Width matches, the vector is already normalised, the id begins `text-embedding-`, and the server itself reports it as an embedding model — so nothing errors, anywhere, ever. Measured against ground truth over 61 parallel Wikipedia articles in en/fr/ja (`npm run search:quality`): cross-lingual retrieval P@1 collapses to **19.7% (en→fr) / 13.1% (en→ja)** against **100% / 98.4%** for the same model family used correctly, discrimination spread is **0.0087 versus 0.3513** — a factor of **40** — every similarity it returns lands in a 0.92–0.94 band whatever you feed it, the worst true translation ranks **61st of 61**, and the ordering is **inverted**: unrelated same-topic documents outscore a document's own translation. (The earlier figure quoted here, margin 0.0080 vs 0.3994 from one query against four documents, was directionally right and is superseded by the above.) The same weights rank correctly through a real `/rerank`: a cross-encoder scores a *(query, document)* pair jointly and has no meaningful standalone vector, so pooling its internals into 1024 floats produces a well-formed number that means nothing. Structural mitigation is the **Rerank** model capability (keeps it out of the embedding picker); `looksLikeCrossEncoder`/`warnIfCrossEncoderEmbedder` (`src/providers/shared.ts`) additionally warn, session-deduped, when an id or reported `arch` matches `/rerank|cross-enc/i` — deliberately a **warn, never a block**, because no field in any local runtime's API structurally distinguishes cross-encoder from bi-encoder, so a naming heuristic is the only signal available and a false positive must not stop indexing. Rerankers only work through a server exposing a real rerank endpoint: **Infinity is not the only one** — `llama-server` has had `--reranking --pooling rank` all along and ships inside LM Studio's own backends, which the earlier "Infinity is the only local reranker" conclusion missed by checking LM Studio's *server* and stopping. Wire-contract difference between them: llama.cpp returns **raw logits** (negative, unbounded — `+1.66` / `−11.03`), Infinity returns **sigmoid-normalised 0–1** (`0.6047`). Higher is better in both so ordering and the strict parser are safe, but any UI, test or threshold asserting a 0–1 range is wrong against llama.cpp, and rerank scores are not comparable across servers.
