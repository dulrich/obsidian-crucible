# src/orchestration/ — job queue, backends, workflows, trackers & intake

Local instructions for the orchestration leg: `Orchestrator.ts`, `{File,Memory}JobBackend.ts`,
`JobStore.ts`, `MemoryJobQueue.ts`, `jobTypeConfig.ts`, `NoteLockManager.ts`,
`TriggerRegistry.ts`, `OrchestrationAutoRunner.ts`, `workflows/`, `utils/`. The root `AGENTS.md`
is the canonical contract; this file adds what is only true here.

Where the boundary sits: the **note lock itself** and the **chain/command registration rules**
that consume it are cross-cutting and stay in the root `AGENTS.md` (they touch `src/main.ts`,
`src/chains.ts`, `src/internalCommands.ts` and `src/localizeAttachments.ts` as much as they
touch this directory). What lives here is the queue, its backends and workflows, and the
tracker/intake pipelines. User-facing writeups: `docs/orchestration.md`,
`docs/tracked-sources.md`, `docs/ingestion-dashboard.md`.

`src/triggers/` (`triggerAdapter.ts`, `guardEval.ts`) is the user-facing half of
`TriggerRegistry` and is documented here rather than in its own file — triggers only ever
*enqueue*, so their semantics are queue semantics.

## Quirks

- **One unified queue, two persistence backends — not two queues.** Every `JobType` declares `persistence: 'file' | 'memory'` in its `JobTypeConfig`, and `Orchestrator.register` builds the matching `JobBackend` (`src/orchestration/{File,Memory}JobBackend.ts`). `FileJobBackend` is the durable, vault-backed path: every job is a markdown file under `orchestrationQueueRoot/{inbox,running,done,failed}`, survives restarts, and is claimed/moved through `JobStore`. `MemoryJobBackend` is deliberately the opposite — an in-memory `MemoryJobQueue` (`src/orchestration/MemoryJobQueue.ts`) that dedupes by `dedupeKey`, auto-drains independent of the autorun toggle, emits live `enrichment-queue-updated` / `metadata-enriched` events, and forgets terminal entries after `terminalRetentionMs`; it **never** touches `JobStore`, because persisting transient UI state as on-disk jobs would spam the vault with throwaway files. The YouTube enrichment queue is exactly this: the `youtube_metadata_fetch` memory type (`youtubeMetadataJobConfig` in `jobTypeConfig.ts`), surfaced to the dashboard through the thin `EnrichmentQueueAdapter`. The two backends are *unified* under one runner: `OrchestrationAutoRunner` drains every type with the same per-type `MinIntervalGate` cooloff and the global `Semaphore` concurrency cap; `Orchestrator`/`AutoRunner` dispatch to `backend.enqueue/runNext/hasPending/refill` rather than branching on `persistence`. So: add a new persistence kind as a new `JobBackend`, not as a parallel queue with its own drain loop, and reuse `MinIntervalGate` for any request pacing rather than reimplementing the spacing math. (A file-backed job whose type later flips to `memory` is unrunnable until `scan()` re-homes it — see the re-home quirk below.)

- **`JobStore.move` rolls the rename back if the frontmatter write fails.** A job's queue bucket is determined by which folder its file lives in (`listFolder` reads by folder), and the frontmatter `status`/`updated` fields must agree with that folder. `move` renames the file into the target folder *then* rewrites the frontmatter; if that second write throws, the file is renamed back to its original path before the error propagates, so a job is never left moved-but-un-updated (e.g. sitting in `done/` while still claiming `status: running`). If you add steps to `move`, preserve the "leave the job fully in its prior bucket on failure" invariant.

- **A file-backed job whose `JobType` is now `memory`-persistence is unrunnable, and `scan()` re-homes it.** Job types declare `persistence: 'file' | 'memory'` in their `JobTypeConfig`. The runner dispatches per type to a `JobBackend`: `MemoryJobBackend` drains an in-memory `MemoryJobQueue` and **never** claims the file folders, while `FileJobBackend` claims markdown jobs from `queued/`. So when a type migrates from file to memory — as `youtube_metadata_fetch` did when enrichment folded into the unified queue — any markdown job left in `inbox/running/` becomes a permanent orphan: nothing drains it, and stale-running recovery only bounces `running→queued`, which is just as un-claimable (it stuck a `youtube_metadata_fetch` job in `running/` with the spinner never clearing). `Orchestrator.scan()` therefore sweeps `queued`+`running` for entries whose current `getConfig(type).persistence === 'memory'`, re-enqueues their params into the memory queue via that type's `backend.enqueue` (which kicks an immediate drain), and archives the markdown file under `done/` with a re-homed note. The heal runs on the **manual "Orchestrate: Scan queue" command only** — there is no auto-scan on load — so after changing a type's persistence, tell users to run Scan once (or run it yourself) to clear strays. If you flip another type to memory, this sweep already covers it; don't reintroduce a file-claim path for memory types.

- **`youtube_metadata_fetch` is one job per *note* (dedupe key `note:<targetPath>`), and the API fetch is the rare path — link-if-exists comes first.** The old shape (dedupe on `videoId`, single job vault-scanning `linkAllNotesForVideoId` to fan the `yt-metadata` link onto every matching note) is gone; don't reintroduce it. `youtubeMetadataJobConfig.dedupeKey` is `targetPath ? 'note:'+targetPath : 'video:'+videoId`, so several captures sharing one video id each get their own queue entry, and each job writes frontmatter on exactly one note. The per-note flow (`YoutubeMetadataFetchWorkflow` → `ingestYoutubeVideoMetadata`) runs under the note lock: bail if `yt-metadata` is already linked, then `ensureMetadataNote(videoId)` (find-or-fetch-create under the `yt-video::<id>` resource lock — see the lock-ordering quirk in the root `AGENTS.md`), then `linkMetadataToNote` on that note only. Because the metadata note is found-not-fetched on every job after the first, N duplicate captures cost one API call total. Standalone entries (uncaptured videos, no vault note yet) keep videoId keying (`video:<id>`) and skip the link write. Anything wanting "all notes for this video get linked" enqueues one per-note job per note (the dashboard's "Enqueue all" and the `yt-metadata-on-capture` trigger both do).

- **`plugin.ingestionEvents` is the source of truth for "ingestion happened" signals.** `FileJobBackend` emits `tracker-run` after each blog/youtube tracker job finishes; the YouTube metadata fetch path (the `youtube_metadata_fetch` memory job, run by `MemoryJobBackend`, plus the standalone `fetchYoutubeMetadataForActiveNote` command) emits `metadata-enriched` after each successful write. The dashboard subscribes to these in addition to Obsidian's `metadataCache.on('changed')` / `vault.on(...)`. If you add a new ingestion path (e.g. a Web Clipper inbox watcher), emit the matching event from there too — the dashboard's live-refresh routing depends on it. `YoutubeMetadataFetchWorkflow` runs in two modes: with `params.targetPath` it calls `ingestYoutubeVideoMetadata` (writes the `yt-metadata` wikilink back onto the note); without one it calls `enrichYoutubeMetadataStandalone` (no back-link write). Don't pass a fake `TFile` to `ingestYoutubeVideoMetadata` — `fileManager.processFrontMatter` will throw.

- **`post-id` canonicalization is platform-aware, not a blind param-strip.** `postIdFromUrl` in `src/orchestration/utils/blogs.ts` is the single chokepoint for both sides of blog dedup: the RSS/Atom parse derives a post's id from it, and the seen-set scan derives the same id from each note's `source` field (`feedSources.ts addSourceUrl`). They must agree, but email-notification links carry extra params the RSS bare slug doesn't (Substack: `publication_id`, `post_id`, `isFreemail`, `r`, `triedRedirect`, `utm_*`). We **cannot** strip all params blindly — on some sites a param like `article_id` *is* the identifier. So `auto` mode runs a `CANON_RULES` table keyed on URL *shape* (the Substack rule matches `/p/<slug>` **plus** a Substack signature param, then drops all params — works on custom domains like emilkirkegaard.com); only if no rule matches does it fall back to the conservative `TRACKING_PARAM_RE` denylist (unknown params preserved). The bare RSS slug has no signature param, so the rule doesn't fire there, yet both the slug and the stripped email link converge on the same `https://host/p/slug`. Override per-blog via the optional **Canon** column in the blogs table (`auto`|`substack`|`strip-params`|`keep-params`); `keep-params` is the escape hatch for sites where a param is the real id. The override reaches the note side (which has no blog context) through `buildBlogCanonHostMap` → a hostname→method map threaded into `buildFeedSeenIdSet`/`ingestFrontmatterIds` as `hostRules`. `lint.ts deriveSourceIdProperties` stays pure `auto` (no blog context); its derived `post-id` is cosmetic — matching correctness lives in the seen-set path, which re-derives from `source` every run, so fixing the canonicalizer repairs already-captured notes without a frontmatter backfill.

- **YT video ID extraction has one home.** `extractVideoIdFromUrl` in `src/orchestration/utils/youtube.ts` owns the regex set (`watch?v=`, `youtu.be/`, `/shorts/`, `/embed/`). `canonicalizeUrl` in `src/orchestration/utils/urlCanonicalize.ts` delegates to it for the ID-extraction step while keeping its own URL-rewriting (host normalization, Shorts → watch, tracking-param strip). Don't add new YT regexes elsewhere — extend `URL_PATTERNS` instead. Shorts URLs and watch URLs yield the same ID, which is the load-bearing assumption behind dedup in `YoutubeTrackerWorkflow`.

- **The Ingestion Dashboard and the consolidation workflows share pure functions in `src/orchestration/utils/{blogsIntake,youtubeIntake}.ts`.** `buildBlogsSeenIdSet` / `buildYoutubeSeenIdSet`, `scanBlogsTrackerRuns` / `scanYoutubeTrackerRuns`, `loadConfiguredBlogs` / `loadConfiguredChannels`, and the intake-run listers are the single source of truth for "what is uncaptured" and "which intake runs exist." Both the dashboard and the `*_consolidate` workflows import them. If you change the algorithm, both surfaces follow — but keep them as pure `(app, ...)`-taking functions so the dashboard can call them outside a `WorkflowContext`. Don't reintroduce the logic inline in the workflow class.

- **Ignored ingestion IDs are folded into the seen set, not checked separately.** `src/orchestration/utils/ignoredIds.ts` stores bare IDs (11-char video IDs; canonical `postIdFromUrl` blog IDs) in the managed note `_crucible/orchestration/ignored.md` under `## Videos` / `## Blogs`. The single chokepoint is the `seedIds` param on `buildYoutubeSeenIdSet` / `buildBlogsSeenIdSet`: every caller (the two tracker workflows, their `*_consolidate` variants, and the dashboard's uncaptured scans) passes `await loadIgnored*Ids(app)`, so ignored items vanish from the uncaptured lists, are filtered out of tracker `newVideos`/`newPosts`, and never auto-enqueue (auto-enrich sources from the now-filtered `uncapturedVideosCache`). Don't add a parallel "is this ignored?" check anywhere — seed the set. The note lives under the `QUEUE_SCAN_SKIP_PREFIX_*` (`_crucible/orchestration/`), so the seen-set vault scan deliberately skips it; it is read explicitly via `loadIgnored*Ids` instead, and writes go through a full read-modify-write re-serialize (`vault.modify`/`create`) since write volume is click-driven. The "YouTube captures without metadata" section is intentionally unaffected — it lists already-captured notes, not tracker candidates.

- **Blog post enrichment writes `_blog_metadata` notes during intake; those notes do not count as captured posts.** The RSS/Atom parsers (`parseRssItems`/`parseAtomEntries` in `src/orchestration/utils/blogs.ts`) extract `authors`, `categories`, `wordCount`, `kind`, and `hasBody`, then `FeedTrackerWorkflow` calls `ensureBlogMetadataNote` so each new post has a durable metadata note under `orchestrationBlogsMetadataRoot` (default `_blog_metadata`). The intake digest still carries a compact trailing HTML comment (`buildBlogBulletSuffix`/`parseBlogBulletMeta`) so old dashboard scans can round-trip lightweight fields, but the body itself lives in the metadata note, converted with Obsidian `htmlToMarkdown`. The dashboard's Uncaptured posts scan must skip `_blog_metadata/**` and `_crucible/**` when building the seen set: metadata notes are staging/enrichment artifacts, not captured vault notes. Rows with `has-body: true` show **Ingest**, which runs the configured queueable/internal command (`orchestrationBlogsIngestCommandId`) against the metadata note as `targetFile`; `read` remains the external blog URL and `metadata` is a link to the metadata file. Body presence is per-blog via the optional **Body** column (`auto`|`full`|`snippet`): `auto` trusts only dedicated content elements, `full` allows fallback `<description>`/Atom `<summary>` for feeds such as Simon Willison, and `snippet` never ingests body. Podcast vs article is decided by audio enclosures, not `itunes:*` channel boilerplate.

- **User-defined Triggers are the *if*; a Chain (or workflow) is the *then* — they compose, they don't merge.** `settings.triggers: TriggerDef[]` are rebuilt into `OrchestrationTrigger`s by `src/triggers/triggerAdapter.ts` (`registerTriggers()` in `main.ts`, mirroring `registerChains()`); like every trigger they only *enqueue*, so a chain action seeds a `chain_run` job (`ChainRunWorkflow`, dedupe `chainName|targetPath`) and a workflow action seeds that job type. Two non-obvious splits: (1) **trigger guards are synchronous** (`fireEvent` runs them inline over the metadata cache), so the condition set reuses `GuardCondition` but only the frontmatter/tag-sourced types in `SYNC_GUARD_CONDITION_TYPES` — `word-count-*` needs an async `cachedRead` and is therefore valid **only as a chain guard step** (`ChainManager.evaluateGuard` is now `async` for exactly this), never as a trigger condition; the settings UI hides it from the trigger condition dropdown. Both surfaces evaluate conditions through the one shared `src/triggers/guardEval.ts` so semantics can't drift. (2) **User triggers carry their own `enabled` flag and are id-namespaced `user:<id>`**, deliberately *not* gated by the founding-trigger `orchestrationTriggersEnabled` map — so the Orchestrate settings tab renders toggles from `triggers.listFounding()`, not `list()`, or every user trigger would double-render there. Adding the `modify` event meant generalizing the debounce to a per-event `pendingByEvent` map (a `modify` burst and a `metadata-changed` burst on the same note must not clobber each other's timer).

- **Daily Brief Lite FX comes from Frankfurter, and its autocompletes cache to settings, not memory.** The FX rate provider is `api.frankfurter.app` (`src/orchestration/utils/fx.ts`), *not* `open.er-api.com` — older UI copy claimed the latter. The currency/location pickers in `Crucible → Settings → Orchestrate → Daily Brief Lite` (`CurrencySuggest` / `LocationSuggest` in `src/suggesters.ts`) are backed by the same two providers: Frankfurter `GET /currencies` for the code list, and Open-Meteo geocoding (`geocoding-api.open-meteo.com/v1/search`) for `City, CC` + coordinates. Two non-obvious things: (1) both override `getSuggestions` as **`async` returning a `Promise`** — Obsidian's `AbstractInputSuggest` allows this, and `LocationSuggest` debounces live geocoding with a `sleep(250)` + `lastQuery`-still-current guard so each keystroke doesn't fire a request; (2) responses are **persisted to plugin settings** (`orchestrationDailyBriefCurrencyCache`, and `orchestrationDailyBriefGeocodeCache` keyed by normalized query), each entry stamped with `fetchedAt`, because these lists change rarely. The cache is invalidated only by the red **Clear cache** buttons next to "Add currency pair" / "Add location" — there is no TTL. If you add another rarely-changing external lookup here, follow the same settings-cache + manual-clear shape rather than a module-level in-memory cache.

- **`newJobId` is millisecond+monotonic, and claim order IS the sorted order — don't reintroduce a coarser stamp or let ordering fall to the random suffix.** Batch fan-outs (`image_describe_batch`, `search_upsert_batch`) mint dozens of ids inside one tick; the original `YYYYMMDD-HHmmss` second-granular stamp left all of them tied, so `JobStore.listFolder`'s comparator fell through to `id.localeCompare` and the random 4-hex suffix decided the order — batches claimed and displayed in random order relative to their `batchIndex`, and since `FileJobBackend.claimNext` takes the first entry of that sort and the queue monitor's default status sort is stable over it, the randomness was visible everywhere. Fix (`plans/image-describe-hardening-ux.md` WP-4): `newJobId` (`src/orchestration/utils/dates.ts`) stamps milliseconds and prepends a **fixed-width** 4-hex in-process counter (reset when the millisecond advances) to the random suffix, so same-millisecond ids sort in mint order; the comparator tie-breaks on `created` (millisecond ISO — lexicographic = chronological) before the id compare. Three invariants to preserve: the counter's fixed width is load-bearing (an under-padded counter overflowing into more digits would silently break lexicographic ordering — same failure family as the NUL/sentinel quirks); every consumer treats the id as an opaque dash-delimited `<stamp>-<type>-<suffix>` string (equality, set membership, `localeCompare`, filename fragment — verified by repo-wide grep; keep it that way, no structural parsing); and the queue monitor's Created column carries raw ISO in `QueueRow.created` for **both** file and memory rows, formatting for humans only at render time — putting a pre-formatted string back into the sort value re-breaks the column's chronological sort across mixed sources.
