# src/orchestration/ — job queue, backends, workflows, trackers & intake

Local instructions for the orchestration leg: `Orchestrator.ts`, `DbJobBackend.ts`,
`db/` (`sqlite.ts`, `SqliteJobStore.ts`, `types.ts`), `jobTypeConfig.ts`, `NoteLockManager.ts`,
`TriggerRegistry.ts`, `OrchestrationAutoRunner.ts`, `workflows/`, `utils/`. The root `AGENTS.md`
is the canonical contract; this file adds what is only true here.

Where the boundary sits: the **note lock itself** and the **chain/command registration rules**
that consume it are cross-cutting and stay in the root `AGENTS.md` (they touch `src/main.ts`,
`src/chains.ts`, `src/internalCommands.ts` and `src/localizeAttachments.ts` as much as they
touch this directory). What lives here is the queue, its backends and workflows, and the
tracker/intake pipelines. User-facing writeups: `docs/orchestration.md`,
`docs/tracked-sources.md`, `docs/ingestion-dashboard.md`.

`src/triggers/` (`triggerAdapter.ts`, `guardEval.ts`) is the user-facing half of
`TriggerRegistry` and is documented here rather than in its own file — triggers only ever
*enqueue*, so their semantics are queue semantics.

## Quirks

- **One durable queue, one backend: every job type is `persistence: 'db'` on `SqliteJobStore`/`DbJobBackend` (thq WP-5..8, 2026-07-30) — jobs are rows in `jobs.sqlite` in the plugin data dir, never vault files.** The store (`db/SqliteJobStore.ts`, opened by `db/sqlite.ts` over `node:sqlite` behind a capability probe) is WAL-mode, self-migrating (meta-table version cookie), and shared by every type; `Orchestrator.register` opens it lazily on the first registration. The contract, piece by piece: (1) **the claim is one atomic `UPDATE … WHERE status='queued'`** (batched candidates, lost race falls through), which makes the old file queue's whole failure class — `JobStore.move`'s rename-then-frontmatter rollback and the "aborted claim" recovery it required — *unrepresentable*, not merely fixed (this entry supersedes the deleted `JobStore.move`/aborted-claim quirks; see git history at `dd8b0b4^` if you need them). (2) **Crash recovery is a lease, not a folder sweep**: rows carry a per-process `claim_token` + `claimed_at`; `recoverStale` (called from every `scan()`, including the silent startup scan) bounces `running → queued` on token mismatch *regardless of age* — so a crashed run recovers on the next plugin load immediately — or on age past the type's timeout + 30s for same-process hangs, and never touches a job `isRunning` says this process still owns. (3) **Terminal rows are pruned by age**: `pruneTerminal` honors `orchestrationJobRetentionDays` (default 30; 0/blank = keep forever) on every scan — the pruning the file queue never had, which is how 37k job files once accumulated. (4) **Stored dedupe keys are type-namespaced `"<type>::<key>"`** because key functions genuinely collide across types (`youtubeMetadataDedupeKey` and `imageDescribeNoteDedupeKey` both mint `note:<path>`); nothing outside `DbJobBackend` reads the column. (5) `hasPending` is an exact indexed `COUNT(*)`, so "empty" is a real answer (which is what makes the auto-source refill hook sound). (6) All store methods take explicit `nowMs` — the backend owns `Date.now()`. Add a future backend as a new `JobBackend` + a `persistence` union member + a `createBackend` case, never as a parallel queue with its own drain loop.

- **A queue-registration failure is caught in `main.ts` and scoped: orchestration dies, the plugin lives.** The first `orchestrator.register` opens the DB; an unopenable one throws `SqliteUnavailableError` (surfaced as a Notice + `logError` inside the Orchestrator — deliberately no silent fallback, because a type registered against nothing would accept enqueues and drop them). `main.ts`'s `registerJobTypes()` wraps all ~20 registrations in one try/catch so the failure leaves zero types registered — every Orchestrator entry point then answers its empty value rather than throwing — while lint, localize, chains, captures and search all still load. Don't move a registration outside that block, and don't "handle" the error by falling back to another storage.

- **The old markdown queue folder (`orchestrationQueueRoot`, default `_crucible/orchestration/queue`) is a frozen archive — nothing reads or writes it, and the setting is LEGACY.** The cutover deliberately imported nothing; a one-time Notice (`archiveNotice.ts`, gated by `orchestrationArchiveNoticeShown`) tells the user the folder is safe to delete manually — the plugin must never auto-delete it (thousands of the user's own vault files). The setting survives for exactly two consumers: that notice's text, and the ingestion dashboard's `route()` queue-root guard — which is *more* load-bearing on deletion day than it ever was in steady state, because deleting a ~20k-note archive fires one vault event per note.

- **`youtube_metadata_fetch` is one job per *note* (dedupe key `note:<targetPath>`), and the API fetch is the rare path — link-if-exists comes first.** The old shape (dedupe on `videoId`, single job vault-scanning `linkAllNotesForVideoId` to fan the `yt-metadata` link onto every matching note) is gone; don't reintroduce it. `youtubeMetadataJobConfig.dedupeKey` is `targetPath ? 'note:'+targetPath : 'video:'+videoId`, so several captures sharing one video id each get their own queue entry, and each job writes frontmatter on exactly one note. The per-note flow (`YoutubeMetadataFetchWorkflow` → `ingestYoutubeVideoMetadata`) runs under the note lock: bail if `yt-metadata` is already linked, then `ensureMetadataNote(videoId)` (find-or-fetch-create under the `yt-video::<id>` resource lock — see the lock-ordering quirk in the root `AGENTS.md`), then `linkMetadataToNote` on that note only. Because the metadata note is found-not-fetched on every job after the first, N duplicate captures cost one API call total. Standalone entries (uncaptured videos, no vault note yet) keep videoId keying (`video:<id>`) and skip the link write. Anything wanting "all notes for this video get linked" enqueues one per-note job per note (the dashboard's "Enqueue all" and the `yt-metadata-on-capture` trigger both do).

- **`plugin.ingestionEvents` is the source of truth for "ingestion happened" signals — and `metadata-enriched` is emitted by the *workflow*, not the queue.** `DbJobBackend` emits `tracker-run` after each blog/youtube tracker job finishes (a generic backend event, keyed off the job type); `metadata-enriched` is per-type and therefore lives with the code that did the write: `YoutubeMetadataFetchWorkflow.emitEnriched` (post-cutover home — the memory queue used to emit it, guarded by a type check that was the one place a generic backend knew a job type by name) and the standalone command path in `internalCommands.ts`. A third ingestion path must emit it too. The former `enrichment-queue-updated` event is gone: its dashboard listener was a strict subset of `orchestration-queue-updated`'s. `YoutubeMetadataFetchWorkflow` runs in two modes: with `params.targetPath` it calls `ingestYoutubeVideoMetadata` (writes the `yt-metadata` wikilink back onto the note); without one it calls `enrichYoutubeMetadataStandalone` (no back-link write). Don't pass a fake `TFile` to `ingestYoutubeVideoMetadata` — `fileManager.processFrontMatter` will throw.

- **`JobTypeConfig.drainsWithoutAutorun` does not do what its name says.** It does NOT bypass the per-type auto-run toggle — `computeShouldDrain` (`autorunGate.ts`) requires `typeAutorun === true` for **every** type, and only then consults the flag. Its live effects are: skip the 5s initial-drain delay after layout-ready, and be skipped by the manual "Run next" (a self-draining type shouldn't consume the user's one explicit run). The name read as a gate bypass when it was a hard-coded property of the deleted `MemoryJobBackend` and outlived that; it became per-type config in thq WP-8 (set on `youtubeMetadataJobConfig`) so collapsing enrichment onto the durable backend didn't silently add a 5s startup delay. The thq WP-8 brief itself asserted the bypass reading and was wrong — expect the next reader to make the same mistake.

- **A job type's auto-ENQUEUE source supplies params, never keys — and a settled job suppresses its own re-seed via a `settled_at` window, not a sweep.** `Orchestrator.setAutoSource(type, fn)` / `refill(type)` (the durable replacement for `MemoryJobQueue`'s auto-source; the drain calls `refill` when a type reports genuinely empty) takes `JobSeed { params, lane? }` — the dedupe key is always derived by the type's own `config.dedupeKey(params)` and type-namespaced by the backend, so a source physically cannot mint a mismatched key. Re-seed suppression is `SqliteJobStore.settledDedupeKeysSince(now − terminalRetentionMs)` (default 60s): without it an enabled source re-offers a just-cancelled item on the very next refill and the user's Cancel reads as ignored. The suppression *expires by design* — a cancelled enrichment item legitimately comes back after the window; a user reporting "Cancel didn't stick" on auto-enqueue is seeing the feature. Auto-ENQUEUE and auto-run stay separate axes (source-enable ≠ execution-enable); the `no-api-key` latch that disables the source lives in `DbJobBackend.failEntry` and gates on the **typed** `failureReason`, never on error-text matching.

- **Triggers are hardened against the self-feeding storm class: plugin-managed paths are excluded at the registry chokepoints, `triggers.start()` waits for layout-ready, the adapter refuses degenerate defs, and enablement is validation-gated (thq WP-1/2).** The incident: "Add trigger" used to persist an *armed* blank wildcard row; it matched every created file including the queue's own job notes, each match minting a `chain_run` job whose job-note create re-fired the trigger — with dedupe defeated (empty chainName ⇒ empty dedupe key ⇒ dedupe skipped) and Obsidian's startup create-replay over the existing job notes re-igniting the loop on every reopen (18k+ jobs). The four layers, each load-bearing: (1) `isPluginManagedPath(path, roots)` (`src/triggers/pluginManagedPath.ts`) with roots `[orchestrationQueueRoot, '_crucible']` — deliberately NOT `_blog_metadata`, whose notes are legitimate trigger targets — applied at all three `TriggerRegistry` chokepoints (`waitForConsistentCache`, `onCacheChanged`, `fireEvent`) and shared by the settings-UI scope estimator. (2) `triggers.start()` runs from `onLayoutReady`, after the create-replay burst, not from `onload`. (3) `triggerAdapter` refuses `chain_run` with empty `chainName` and `command_run` with empty `commandId`, and an empty `events` list adapts to nothing (no silent `['create']` default). (4) `newTrigger()` mints `enabled: false`; both Enable toggles gate on `validateTrigger` (`src/triggers/triggerValidation.ts` — `errors` block enabling, `warnings` surface beside the debounced "~N notes currently in scope" estimate); `registerTriggers()` filters invalid defs with a `logWarn` and **never rewrites data.json**, so a hand-edited invalid def can't arm but also isn't destroyed.

- **`post-id` canonicalization is platform-aware, not a blind param-strip.** `postIdFromUrl` in `src/orchestration/utils/blogs.ts` is the single chokepoint for both sides of blog dedup: the RSS/Atom parse derives a post's id from it, and the seen-set scan derives the same id from each note's `source` field (`feedSources.ts addSourceUrl`). They must agree, but email-notification links carry extra params the RSS bare slug doesn't (Substack: `publication_id`, `post_id`, `isFreemail`, `r`, `triedRedirect`, `utm_*`). We **cannot** strip all params blindly — on some sites a param like `article_id` *is* the identifier. So `auto` mode runs a `CANON_RULES` table keyed on URL *shape* (the Substack rule matches `/p/<slug>` **plus** a Substack signature param, then drops all params — works on custom domains like emilkirkegaard.com); only if no rule matches does it fall back to the conservative `TRACKING_PARAM_RE` denylist (unknown params preserved). The bare RSS slug has no signature param, so the rule doesn't fire there, yet both the slug and the stripped email link converge on the same `https://host/p/slug`. Override per-blog via the optional **Canon** column in the blogs table (`auto`|`substack`|`strip-params`|`keep-params`); `keep-params` is the escape hatch for sites where a param is the real id. The override reaches the note side (which has no blog context) through `buildBlogCanonHostMap` → a hostname→method map threaded into `buildFeedSeenIdSet`/`ingestFrontmatterIds` as `hostRules`. `lint.ts deriveSourceIdProperties` stays pure `auto` (no blog context); its derived `post-id` is cosmetic — matching correctness lives in the seen-set path, which re-derives from `source` every run, so fixing the canonicalizer repairs already-captured notes without a frontmatter backfill.

- **YT video ID extraction has one home.** `extractVideoIdFromUrl` in `src/orchestration/utils/youtube.ts` owns the regex set (`watch?v=`, `youtu.be/`, `/shorts/`, `/embed/`). `canonicalizeUrl` in `src/orchestration/utils/urlCanonicalize.ts` delegates to it for the ID-extraction step while keeping its own URL-rewriting (host normalization, Shorts → watch, tracking-param strip). Don't add new YT regexes elsewhere — extend `URL_PATTERNS` instead. Shorts URLs and watch URLs yield the same ID, which is the load-bearing assumption behind dedup in `YoutubeTrackerWorkflow`.

- **The Ingestion Dashboard and the consolidation workflows share pure functions in `src/orchestration/utils/{blogsIntake,youtubeIntake}.ts`.** `buildBlogsSeenIdSet` / `buildYoutubeSeenIdSet`, `scanBlogsTrackerRuns` / `scanYoutubeTrackerRuns`, `loadConfiguredBlogs` / `loadConfiguredChannels`, and the intake-run listers are the single source of truth for "what is uncaptured" and "which intake runs exist." Both the dashboard and the `*_consolidate` workflows import them. If you change the algorithm, both surfaces follow — but keep them as pure `(app, ...)`-taking functions so the dashboard can call them outside a `WorkflowContext`. Don't reintroduce the logic inline in the workflow class.

- **Ignored ingestion IDs are folded into the seen set, not checked separately.** `src/orchestration/utils/ignoredIds.ts` stores bare IDs (11-char video IDs; canonical `postIdFromUrl` blog IDs) in the managed note `_crucible/orchestration/ignored.md` under `## Videos` / `## Blogs`. The single chokepoint is the `seedIds` param on `buildYoutubeSeenIdSet` / `buildBlogsSeenIdSet`: every caller (the two tracker workflows, their `*_consolidate` variants, and the dashboard's uncaptured scans) passes `await loadIgnored*Ids(app)`, so ignored items vanish from the uncaptured lists, are filtered out of tracker `newVideos`/`newPosts`, and never auto-enqueue (auto-enrich sources from the now-filtered `uncapturedVideosCache`). Don't add a parallel "is this ignored?" check anywhere — seed the set. The note lives under the `QUEUE_SCAN_SKIP_PREFIX_*` (`_crucible/orchestration/`), so the seen-set vault scan deliberately skips it; it is read explicitly via `loadIgnored*Ids` instead, and writes go through a full read-modify-write re-serialize (`vault.modify`/`create`) since write volume is click-driven. The "YouTube captures without metadata" section is intentionally unaffected — it lists already-captured notes, not tracker candidates.

- **Blog post enrichment writes `_blog_metadata` notes during intake; those notes do not count as captured posts.** The RSS/Atom parsers (`parseRssItems`/`parseAtomEntries` in `src/orchestration/utils/blogs.ts`) extract `authors`, `categories`, `wordCount`, `kind`, and `hasBody`, then `FeedTrackerWorkflow` calls `ensureBlogMetadataNote` so each new post has a durable metadata note under `orchestrationBlogsMetadataRoot` (default `_blog_metadata`). The intake digest still carries a compact trailing HTML comment (`buildBlogBulletSuffix`/`parseBlogBulletMeta`) so old dashboard scans can round-trip lightweight fields, but the body itself lives in the metadata note, converted with Obsidian `htmlToMarkdown`. The dashboard's Uncaptured posts scan must skip `_blog_metadata/**` and `_crucible/**` when building the seen set: metadata notes are staging/enrichment artifacts, not captured vault notes. Rows with `has-body: true` show **Ingest**, which runs the configured queueable/internal command (`orchestrationBlogsIngestCommandId`) against the metadata note as `targetFile`; `read` remains the external blog URL and `metadata` is a link to the metadata file. Body presence is per-blog via the optional **Body** column (`auto`|`full`|`snippet`): `auto` trusts only dedicated content elements, `full` allows fallback `<description>`/Atom `<summary>` for feeds such as Simon Willison, and `snippet` never ingests body. Podcast vs article is decided by audio enclosures, not `itunes:*` channel boilerplate.

- **User-defined Triggers are the *if*; a Chain (or workflow) is the *then* — they compose, they don't merge.** `settings.triggers: TriggerDef[]` are rebuilt into `OrchestrationTrigger`s by `src/triggers/triggerAdapter.ts` (`registerTriggers()` in `main.ts`, mirroring `registerChains()`); like every trigger they only *enqueue*, so a chain action seeds a `chain_run` job (`ChainRunWorkflow`, dedupe `chainName|targetPath`) and a workflow action seeds that job type. Two non-obvious splits: (1) **trigger guards are synchronous** (`fireEvent` runs them inline over the metadata cache), so the condition set reuses `GuardCondition` but only the frontmatter/tag-sourced types in `SYNC_GUARD_CONDITION_TYPES` — `word-count-*` needs an async `cachedRead` and is therefore valid **only as a chain guard step** (`ChainManager.evaluateGuard` is now `async` for exactly this), never as a trigger condition; the settings UI hides it from the trigger condition dropdown. Both surfaces evaluate conditions through the one shared `src/triggers/guardEval.ts` so semantics can't drift. (2) **User triggers carry their own `enabled` flag and are id-namespaced `user:<id>`**, deliberately *not* gated by the founding-trigger `orchestrationTriggersEnabled` map — so the Orchestrate settings tab renders toggles from `triggers.listFounding()`, not `list()`, or every user trigger would double-render there. Adding the `modify` event meant generalizing the debounce to a per-event `pendingByEvent` map (a `modify` burst and a `metadata-changed` burst on the same note must not clobber each other's timer).

- **Daily Brief Lite FX comes from Frankfurter, and its autocompletes cache to settings, not memory.** The FX rate provider is `api.frankfurter.app` (`src/orchestration/utils/fx.ts`), *not* `open.er-api.com` — older UI copy claimed the latter. The currency/location pickers in `Crucible → Settings → Orchestrate → Daily Brief Lite` (`CurrencySuggest` / `LocationSuggest` in `src/suggesters.ts`) are backed by the same two providers: Frankfurter `GET /currencies` for the code list, and Open-Meteo geocoding (`geocoding-api.open-meteo.com/v1/search`) for `City, CC` + coordinates. Two non-obvious things: (1) both override `getSuggestions` as **`async` returning a `Promise`** — Obsidian's `AbstractInputSuggest` allows this, and `LocationSuggest` debounces live geocoding with a `sleep(250)` + `lastQuery`-still-current guard so each keystroke doesn't fire a request; (2) responses are **persisted to plugin settings** (`orchestrationDailyBriefCurrencyCache`, and `orchestrationDailyBriefGeocodeCache` keyed by normalized query), each entry stamped with `fetchedAt`, because these lists change rarely. The cache is invalidated only by the red **Clear cache** buttons next to "Add currency pair" / "Add location" — there is no TTL. If you add another rarely-changing external lookup here, follow the same settings-cache + manual-clear shape rather than a module-level in-memory cache.

- **`newJobId` is millisecond+monotonic, and claim order IS the sorted order — don't reintroduce a coarser stamp or let ordering fall to the random suffix.** Batch fan-outs (`image_describe_batch`, `search_upsert_batch`) mint dozens of ids inside one tick; the original `YYYYMMDD-HHmmss` second-granular stamp left all of them tied, so the claim-order comparator fell through to `id.localeCompare` and the random 4-hex suffix decided the order — batches claimed and displayed in random order relative to their `batchIndex`, visibly everywhere since `claimNext` takes the head of that order. Fix (`plans/image-describe-hardening-ux.md` WP-4): `newJobId` (`src/orchestration/utils/dates.ts`) stamps milliseconds and prepends a **fixed-width** 4-hex in-process counter (reset when the millisecond advances) to the random suffix, so same-millisecond ids sort in mint order; the order — now SQL, `ORDER BY lane_rank, priority_rank, created, id` in `SqliteJobStore` — tie-breaks on `created` (millisecond ISO — lexicographic = chronological) before the id compare. Three invariants to preserve: the counter's fixed width is load-bearing (an under-padded counter overflowing into more digits would silently break lexicographic ordering — same failure family as the NUL/sentinel quirks); every consumer treats the id as an opaque dash-delimited `<stamp>-<type>-<suffix>` string (equality, set membership, `localeCompare` — verified by repo-wide grep; keep it that way, no structural parsing); and the queue monitor's Created column carries raw ISO in `QueueRow.created`, formatting for humans only at render time — putting a pre-formatted string back into the sort value re-breaks the column's chronological sort.

- **Image-describe failures are classified `transient` vs `permanent` at record-write time, and infra failures trip a breaker instead of writing skip-forever records.** The `kind: 'failed'` store record's skip-forever semantics (`has()` stays true; no chunks, no facet, never moves `contentHash`) were designed for *poison images* — but the first live batches wrote 1,039 failed records of which ~1,030 were infra casualties: 954 `timed out after 120000ms` (a timed-out request is abandoned client-side but keeps generating server-side, so every subsequent image queues behind it and times out too) and 85 `net::ERR_CONNECTION_*` (router down → dozens of skip-forever records per second). The layers, each load-bearing: (1) `classifyFailure(message)` in `src/search/imageDescriptionStore.ts` is the single source of truth for `failureClass` (`/timed out after \d+ms|net::ERR_/` → `transient`, else `permanent`; legacy records without the field classify lazily by message). (2) The breaker in `src/orchestration/utils/imageDescribe.ts`: a connection-class error (`CONNECTION_CLASS_ERROR_RE` — REFUSED/RESET/NETWORK_CHANGED, deliberately narrower than `classifyFailure`) writes **no record at all** and aborts the batch; 3 consecutive timeouts also abort (their records *are* written, as transient) — remaining images stay pending. (3) The abort surfaces as a `deferred` job result with `serviceUnhealthy` naming `SERVICE_IMAGE_DESCRIPTION_PROVIDER`, so the drain stops claiming describe jobs while the provider is down and the *same job* re-queues; `has()` makes the resume idempotent. The note/batch job configs declare the service; the backfill deliberately does **not** (it must be able to run its prune step regardless). (4) The backfill prunes transient-class failed records at start (`pruneFailed('transient')`), and `load()` deletes zero-byte/corrupt record JSONs; the "Search: retry failed image descriptions" command offers transient-only or all. If you add another provider-driven batch workflow, reuse this taxonomy — never let an infra outage mint permanent skip records.
