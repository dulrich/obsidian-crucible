But the review's headline finding is structural: **WP-4's word-count fix is a per-key workaround for a class-level defect the codebase has already met twice and solved properly once.** This plan is the remediation contract for a later orchestrator session — do not execute it in the review session that produced it.

## Findings (ranked)

1. **The stale-metadata-cache race is a class, and WP-4 patched one symptom of it.** Three manifestations are now on record:
   - *Trigger evaluation (read side)* — triggers fired against stale cached frontmatter. Fixed **properly** in `a3e2e7a` per `plans/metadata-consistent-trigger-evaluation.md`: `TriggerRegistry` records raw events and evaluates only on `metadataCache.on('changed')` (`waitForConsistentCache`/`onCacheChanged`, `TriggerRegistry.ts:142-166`). This is the codebase's established consistency-barrier pattern.
   - *Frontmatter writes (write side)* — `fileManager.processFrontMatter` merges the callback's mutations against the cache's `frontmatterPosition`; when the cache hasn't re-indexed the current bytes (post-rename + rapid edit, the Ingest-as-News window), the write lands on the wrong byte range and the value is silently lost. **Every** frontmatter write flows through the unguarded pass-through `updateFrontmatter` (`src/frontmatter.ts:14`) — 20 call sites across 7 files (`JobStore.ts` ×9, `lint.ts` ×3, `ratingPanel.ts` ×2, `LinkScanWorkflow.ts` ×2, `main.ts` ×2, `FeedTrackerWorkflow.ts`, `youtubeApi.ts`) plus one direct `processFrontMatter` in `imageMetadata.ts:62`. All are exposed. WP-4's `setFrontmatterWordCount` reasserts exactly one key at one of them.
   - *Editor-buffer authority* — a stale open-editor buffer clobbering post-rename disk writes; handled by `ChainManager.reconcileOpenEditor`. This one is legitimately a separate mechanism (editor autosave, not the metadata cache) and stays.

   The root fix is to give the write side the same barrier the read side already has, at the existing chokepoint — after which the per-key reassert is deleted.
2. **CONFIRMED corruption bug inside the workaround itself** — reinforcing that it should be deleted, not fixed. `setFrontmatterWordCount` (`src/lint.ts:49`) rebuilds via `m[0].replace(block, newBlock)`; with an empty frontmatter block (`---\n\n---\n`, plausible precisely when the race dropped the earlier write), `replace('')` inserts at index 0. Reproduced: `setFrontmatterWordCount('---\n\n---\n\nBody prose.', 42)` → `"\nword-count: 42---\n\n---\n\nBody prose."` — the key lands **before** the opening `---`, destroying the frontmatter block.
3. **Canonical-layer leak with a realized defect — secret-registry bookkeeping lives in UI closures, and a third call site missed it.** `record`/`forget` are wired inside `mountSecretControl` closures at three sites (`ai.ts` ×2 — copy-pasted verbatim — and `orchestration.ts`) instead of beside the store operations. `deleteProvider` (`ai.ts:94`) clears the key but never forgets it → a deleted provider can warn "API key missing" forever, labeled with the raw key name (provider gone, so `describeSecretKey` can't resolve it). Related: clear-by-empty-write + grow-by-observation re-registers intentionally cleared keys that `listSecrets()` still lists.
4. **WP-2 shipped a model without its writers.** `orchestrationJobTypeAutorun` only ever mirrors `ingestionYoutubeAutoEnrichEnabled`; no UI writes any other type's entry, so `computeShouldDrain`'s file-type veto branch and `effectiveTypeAutorun`'s file-type flag branch are unreachable — and the two functions encode **divergent** file-type semantics (per-type `true` displays "auto-run" while the gate still requires global Autorun). The Queue Monitor "controls" are a read-only chip + Run button, not the locked toggle + rate-limit.
5. **Scattered sync rituals.** Two UI sites hand-perform the tri-flag enrichment sync {legacy flag, `setJobTypeAutorun`, `setAutoEnabled`}, a third render-time site re-enables on paint (`ingestionDashboard.ts:471-478`), and every manual-enqueue site must remember `runType('youtube_metadata_fetch')` (two comment-ritualized sites today).
6. **Threaded `manual` boolean + dual drain-sets in `OrchestrationAutoRunner`** (`drainingTypes`/`manualDrainingTypes`, `has(x) || has(x)` twice) — a one-off mode flag; a single `Map<JobType, 'auto' | 'manual'>` deletes the parallelism.
7. **Vestigial `Linter` dependency in `AttachmentLocalizer`.** Sole remaining use (`localizeAttachments.ts:413`) is exactly `isPathExcluded(this.settings, path, 'lint')`, the form `repairFolder` already uses; the constructor dep can go.

Non-WP observations: (a) `main.ts` (1314→1361) and `ingestionDashboard.ts` (1284→1332) were already over the 1k boundary and keep accreting; WP-R3 moves the new dashboard code out, and a dedicated decomposition plan is warranted soon. (b) `Record<string, boolean>` → `Partial<Record<JobType, …>>` and the duplicated map-normalization guard — folded into WP-R3.

## Summary

Four packages: the class-level frontmatter write-consistency barrier, deleting WP-4's per-key workaround (R1); a secret-store facade moving registry bookkeeping to the canonical layer (R2); completing WP-2's locked per-type controls while unifying the gate model and de-scattering the sync/kick rituals (R3); deleting the localizer→linter coupling (R4). R1/R3 are orchestrator-direct on shared contracts; R2 is subagent-friendly; R4 is trivial.

## Key Changes

**WP-R1 — Frontmatter write-consistency barrier at the chokepoint (~0.3 kSLOC touched, net-negative, ~180k tokens).** Mirror the read-side pattern (`TriggerRegistry.waitForConsistentCache`) on the write side, inside `updateFrontmatter` (`src/frontmatter.ts:14`), so all 20 call sites are protected at once: (1) **Staleness check** — read raw content and compare the cache's `frontmatterPosition` offsets (or key set) against the actual block located by `FRONTMATTER_REGEX`; matching → proceed immediately (no added latency on the common path). (2) **Barrier** — when stale, await that file's next `metadataCache.on('changed')` (scoped listener, `offref` on resolve) with a bounded timeout (~2s); the indexer runs independently of plugin note-locks, so waiting under `withOptionalNoteLock`/`withMaterializing` cannot deadlock, and the wait happens *before* the write so it never awaits its own event. (3) **Timeout path** — log a warning, run the write anyway, then verify the mutated keys landed via a raw re-read; escalate the log if not (observability, not silent loss). (4) Route `imageMetadata.ts:62`'s direct `processFrontMatter` through `updateFrontmatter` — chokepoint becomes total. (5) **Delete `setFrontmatterWordCount`**, its lint call, and its tests (the blank-line `vault.process` normalization pass stays); this removes finding 2's corruption bug by removal. If implementation reveals the barrier is insufficient for some window and a content-based fallback must stay, that fallback must splice by index, never `String.replace(block, …)`. (6) Update the AGENTS.md `processFrontMatter` quirk entry: the canonical fix is the barrier in `updateFrontmatter`; future writers get it for free. Tests: unit-test staleness detection + barrier with a stubbed `metadataCache`; regression test simulating the stale-cache drop (write survives with barrier). Files: `src/frontmatter.ts`, `src/lint.ts`, `src/orchestration/utils/imageMetadata.ts`, `AGENTS.md`, `tests/` (new frontmatter-barrier suite; prune `lint.wordcount` reassert tests). *Model: top (Claude Opus/high — a contract change under every frontmatter write in the plugin; Codex Sol/medium-high). Execution: Claude direct (must-direct: shared write contract, subtle cache semantics); Codex direct (must-direct: same).*

**WP-R2 — Secret-store facade: registry bookkeeping at the canonical layer (~0.35 kSLOC touched, ~155k tokens).** A single plugin-owned secrets facade (natural home: extend `src/secretRegistry.ts`) wrapping `app.secretStorage` get/set/clear for all `crucible-` keys, performing `record`/`forget` inside `store`/`clear`; route `ProviderManager.{load,store,delete}ApiKey` and the `youtubeApi.ts` helpers through it (keeps the sync-or-Promise `await` handling in one place instead of three comment-annotated call sites). Fixes the `deleteProvider` miss automatically; deletes the `record`/`forget` wiring from all three `mountSecretControl` closures — extract the twice-copy-pasted provider closure block in `ai.ts` into one helper while there. Harden reconcile against clear-by-empty: treat a listed key whose `getSecret` value is empty as absent, so cleared keys neither re-register nor false-report. Extend `tests/secretRegistry.test.mjs` (empty-value, deleted-provider cases). Files: `src/secretRegistry.ts`, `src/providers.ts`, `src/orchestration/utils/youtubeApi.ts`, `src/settings/sections/ai.ts`, `src/settings/sections/orchestration.ts`, `src/settings/shared.ts`, `src/main.ts`, tests. *Model: mid (Claude Sonnet/medium; Codex Terra/medium). Execution: Claude subagent (isolated seam; 155k×0.6 = 93k vs 155k direct = 40% saving; ≤200k so direct is also defensible); Codex subagent (77.5k vs 155k, 50% saving).*

Files: `src/localizeAttachments.ts`, `src/main.ts`, tests if any stub the ctor. *Model: mid (Claude Sonnet/medium; Codex Terra/medium). Execution: Claude direct (tiny ≤200k); Codex direct (tiny ≤200k).*

- `getSecret` probing during reconcile is acceptable at startup cost (a handful of keys, already async).
- The `orchestrationJobTypeControls` reshape happens while the old map has existed for exactly one unreleased sprint — one-shot migration, no long-tail compat.
- WP-R3's rate-limit override plumbs into the existing per-type `minIntervalMs` drain-pacing config; if that point lives elsewhere, file scope holds but wiring line-count may shift.
