# docker/llamacpp-vulkan/ — local inference container

Local instructions for the Vulkan llama.cpp inference container. The root `AGENTS.md` is the
canonical contract; this file adds what is only true here. Provider-side wire-protocol rules
(which provider kind LM Studio is, rerank endpoints) live in `src/providers/AGENTS.md`; the
user-facing writeup is `docs/local-inference.md`.

Files here: `Dockerfile`, `entrypoint.sh`, `config.yaml` (llama-swap), `smoke-inference.sh`,
`README.md`. Nothing in this directory is covered by `npm run lint` / `tsc` — the root Full
Cleanup Loop still applies to any TypeScript you touch alongside it.

## Quirks

- **A local inference service that came up healthy has told you nothing — this stack's GPU and capability failures are all "the guard passes and the thing is wrong".** Four instances of one shape, each of which cost real time: (1) **`torch.cuda.is_available()` returns `True`** on an AMD Infinity image whose compiled arch list stops at `gfx1100`/`gfx942`, so a GPU switch on gfx1201 passes its healthcheck and dies on the first real kernel. (2) **A Vulkan loader with no usable hardware driver still enumerates `llvmpipe`**, a software rasteriser, as a completely valid device — it is present even on a working host alongside the real GPU — so an image whose Mesa is too old to claim the GPU starts, answers every request *correctly*, passes any port-is-open healthcheck, and runs **several times slower than the CPU containers it replaced**. A silent CPU fallback is a regression wearing the costume of a working service; `docker/llamacpp-vulkan/entrypoint.sh` therefore asserts `PHYSICAL_DEVICE_TYPE_DISCRETE_GPU`/`INTEGRATED_GPU` before exec and logs what ggml resolved, and the `debian:sid-slim` base (Mesa 26.1.5) is load-bearing rather than lazy — trixie and Ubuntu 24.04 ship 24.x/25.0.x. (3) **LM Studio answers unknown endpoints with HTTP 200** and `{"error":"Unexpected endpoint or method. (POST /x)"}` in the body, so a status-code capability probe reports every capability as present — this is exactly how `/v1/rerank` was first mistaken for supported. **Probe by response body, not status code.** (4) A written API description is not a wire format: the brief's `quant` field is really `quantization` in a live LM Studio response, and trusting the description would have made every LM Studio model report `precision: undefined`, indistinguishable from Infinity's genuine unknown. Related: Infinity's `--engine optimum` needs *published ONNX* weights and dies at engine selection with `No onnx files found` for a PyTorch-only repo like `bge-reranker-v2-m3` (looks like a memory or network problem; is neither), and base URLs are asymmetric on purpose — `openai-compatible` embedding needs the `/v1` suffix because the client appends `/embeddings`, while Infinity's rerank route is unprefixed. Do not attempt ROCm on gfx1201 via `HSA_OVERRIDE_GFX_VERSION`: invalid GPU programs are the workload class that wedges this GPU, and `context-control/references/rdna4-gpu-hang.md` has the signature and the recovery paths.
