# Crucible Plugin (Development Guide)

## Project overview

- **Target:** Obsidian Community Plugin (TypeScript → bundled JavaScript).
- **Consolidation:** Replaces features from Daily Notes, Templater, Shell Commands, Linter, and QuickAdd.
- **Entry point:** `src/main.ts` compiled to `main.js` and loaded by Obsidian.
- **Artifacts:** `main.js`, `manifest.json`, and `styles.css`.

## Environment & tooling

- Node.js: use current LTS.
- **Bundler:** esbuild (configured via `esbuild.config.mjs`).
- **Types:** `obsidian` type definitions.

### Commands

```bash
npm install     # Install dependencies
npm run dev     # Watch for changes and hot-recompile
npm run build   # Production build with minification
npm run lint    # Run ESLint and Stylelint
```

## Full Cleanup Loop (MANDATORY)

Before signaling task completion or reporting success, you MUST execute and pass this sequence. **Run these commands sequentially (do not background them) so that output is immediately visible:**

1.  **Linting:** Run `npm run lint`. This executes both ESLint (for TypeScript) and Stylelint (for CSS). All errors MUST be resolved.
2.  **Type Checking:** Run `npx tsc -noEmit -skipLibCheck`. The project must have zero TypeScript errors.
3.  **Build:** Run `node esbuild.config.mjs production`. Ensure the bundling completes successfully and updates `main.js`.
4.  **Verification:** Confirm all processes exited with code 0.

## Debugging Protocol (UI/UX)

If a UI/UX bug is not resolved on the first attempt, or if the root cause is not immediately obvious from code inspection, you MUST prompt the user for path-dependency details before continuing:
- **Input Method:** Did the issue occur via mouse click, keyboard (e.g., Enter vs. Tab), or command palette?
- **State Context:** What was the specific state of the active note and target note (e.g., selection active, focus location)?
- **Trigger Specifics:** Does the behavior change if a different UI element is used to trigger the same logic?

When debugging a UI-observable Obsidian plugin failure, do not compensate for missing runtime evidence by expanding scope. Add targeted instrumentation or request a sandboxed UI rerun.

If the next useful evidence would come from seeing the UI, stop and return a rerun packet instead of inspecting Obsidian internals.

A valid rerun packet includes:
- patch applied
- command to rebuild/reload
- exact UI steps
- expected console/log output
- what to report back

## UI & UX Standards

- **Crucible builds primarily against the N1 Console design system**, adapted where Obsidian's built-in UI requires it. The component specs live in the shared `signalworks-design` skill (`~/.claude/skills/signalworks-design/`, canonical source `context-control/skills/`) — consult them before inventing a treatment or copying a nearby ad-hoc rule. Two rules that look contradictory and are not:
  - **The design language comes from N1**: the pill taxonomy (status / tag / neutral), pill geometry, status semantics, and the fixed lucide icon mapping (one concept = one icon fleet-wide).
  - **The expression stays in Obsidian semantic vars**: write `var(--text-muted)`, never `var(--n1-muted)`. `theme/theme.css`'s adapter maps N1 tokens onto Obsidian's names, and that indirection is exactly what lets the theme reskin plugin views for free (see the N1 Console quirk below). **Never reach for an `--n1-*` token from `styles.css`.**
- **Pills follow the fleet taxonomy, and picking the wrong family is a real error, not a nitpick.** `.crucible-pill` + a variant is the shared primitive. **Status** pills (ANSI hue label + border + 5%-tint background) are for ok/warn/error/info and must never be the sole carrier of that meaning. **Neutral** pills — `.is-muted` / `.is-contrast`, transparent background, border and label the same colour, same geometry — are for *non-semantic* states: disabled, n/a, counts-at-rest, and constraints like the Queue Configuration `serial` marker. Spending a status hue on a non-status fact spends the reader's alarm budget on nothing. Geometry is what makes a pill read as one: `border-radius: 99px`, not a corner rounding.
- **Destructive controls carry `mod-warning`**, and never sit flush against a non-destructive one — give the row's action cell a `gap` (see `.crucible-queue-action-cell`). Adjacent Run/Cancel buttons with no spacing are a misclick waiting to happen.
- **Grouped Cards:** All settings must be organized within `.crucible-settings-group` containers to match the native Obsidian "Options" look.
- **Inset Dividers:** Use `hr` with `.crucible-row-divider` for separators that don't touch the edges.
- **Widths:** Use the standardized CSS classes: `.pi-width-half` (150px), `.pi-width-normal` (300px), or `.pi-width-wide` (450px). NEVER use hardcoded pixel widths for controls in CSS.
- **Centering:** Vertical centering in settings rows is currently handled by the default Obsidian layout; do not attempt complex flex overrides without careful testing.
- **Tabs:** The settings page is divided into "Settings", "Shortcuts", "Captures", "Lint", and "Variables".
- **Fuzzy Search:** Use the custom `FileSuggest` and `FolderSuggest` classes for any file-path inputs.
- **List + edit pattern:** Tabs that manage a collection (Captures, Chains, Providers, Agents, Workflows) render a list of rows on the main view — each with an Enable toggle (when applicable) and a pencil button — and flip into a per-item detail editor with a `← Back` button via the `editing*Index` / `editingWorkflowId` state on `CrucibleSettingTab`. New collection-style tabs should follow this pattern instead of inlining all fields.

## Template Engine

Supported tokens in any template or property injection:
- `{{date}}`: Target date of the note (YYYY-MM-DD).
- `{{time}}`: Target time of the note (HH:mm).
- `{{today}}`: System date at invocation (YYYY-MM-DD).
- `{{now}}`: System ISO datetime at invocation.
- `{{title}}`: Resolved note title (from property or filename).
- `{{value}}`: User input (supported in Captures).
- `{{value:oneline}}`: User input with all whitespace runs (including newlines/paragraph breaks) collapsed to single spaces — for inserting multi-paragraph input into list items.
- `{{datetime:FORMAT}}`: Custom Moment.js format string.

Additional tokens available in **attachment** folder/name templates (`applyAttachmentTemplate` in `src/utils.ts`):
- `{{folder}}`: The note's parent folder path.
- `{{slug}}`: Lowercase-sluggified note basename.
- `{{name}}`: Note basename (alias of `{{title}}`).
- `{{ext}}`: Attachment extension (no dot).
- `{{md5}}`: Hex MD5 of the attachment bytes (only in the name template).
- `{{original}}`: Original attachment filename without extension.

## Coding Conventions

- **Safe YAML:** Always route metadata updates through `updateFrontmatter` (`src/frontmatter.ts`) — never call `fileManager.processFrontMatter` directly. The wrapper adds the stale-cache write barrier (see the quirk below) on top of `processFrontMatter`'s structural integrity.
- **Recursive Safety:** Use the `isMaterializing` flag to wrap all plugin-driven file modifications to prevent infinite loops (especially with "Lint on Save").
- **Path Awareness:** Always check `isPathIgnored` from the `Linter` class before running automated note body operations.

## Quirks

Non-obvious Obsidian/runtime behaviors that bit us once and would bite again. Add entries here when a fix turned out to hinge on something the API docs don't surface.

- **Shared Claude Code skills (tn-code-review, plan-workflow, tests-lint, project-setup, migrations-release-cleanup) are NOT in this repo.** They live canonically in `/home/_shared_code/context-control/skills/` and are installed machine-wide as symlinks into `~/.claude/skills/` by that repo's `skills/install.sh`. This repo's local `.claude/skills/tn-code-review` copy was deleted in favor of the shared one — if a skill seems missing, re-run `context-control/skills/install.sh` rather than restoring a local copy (local copies drift).

- **`Lint: word count` is prose-only — it strips markup before segmenting.** `calculateWordCount` in `src/lint.ts` runs `stripNonProseContent` (after removing frontmatter, before `Intl.Segmenter`), which deletes fenced/inline code, HTML comments, `<svg>`/`<script>`/`<style>` blocks, and image embeds, and reduces `[text](url)`/`[[page|alias]]` links to their visible text. This exists because web-clipped articles embed inline `<svg>` Highcharts charts whose hundreds of `<path d="M 0 98.75 L …">` coordinate tokens each register as `isWordLike` — one chart pushed a real ~1k-word article to `word-count: 7375`. Don't "simplify" it back to strip-frontmatter-only, and don't be alarmed that re-linting legacy notes lowers their `word-count`: that's the count being corrected, not a regression. `stripNonProseContent` and the now-module-level `calculateWordCount` are exported for unit tests (`tests/lint.wordcount.test.mjs`); the `Linter.calculateWordCount` method is a thin wrapper. The strip steps are order-sensitive (outer/greedy constructs first) — see the comment above `stripNonProseContent`.
- **`FuzzySuggestModal.selectSuggestion` closes before it chooses.** The base implementation calls `this.close()` *before* `onChooseSuggestion`/`onChooseItem`, so any "did the user pick something?" flag set inside `onChooseItem` is too late — `onClose` has already run with the flag still false. If the modal uses an `onCancel` callback distinct from `onChoose`, override `selectSuggestion` to flip the flag (and invoke the resolve callback) *before* calling `super`, or skip `super` and call `close()` yourself. See `src/modelPicker.ts`.
- **Commands must be registered via `this.registerCrucibleCommand({ ..., group })`, not `this.addCommand` directly.** The settings UI (`Crucible → Settings → Commands`) renders from `plugin.commandRegistry`, which is populated only by the helper. A command registered with `this.addCommand` will work but be invisible to the visibility toggles — that's how `lint-cleanup-transcript` slipped through. The `group` literal (`'Lint'`, `'Materialize'`, `'Orchestrations'`, etc.) controls which section it appears in; new groups need an entry in the `CrucibleCommandGroup` union in `src/main.ts` and the `GROUP_ORDER` array in `src/settings.ts`. For dynamic command sets (Shortcuts, Captures, Chains, Agents), the re-register methods call `clearCommandRegistryGroup(group)` first to avoid duplicate entries.
- **`Lint: localize attachments` is NOT part of `Lint: all`.** It's a standalone command in `src/localizeAttachments.ts` that touches binary files and (when downloading remote URLs) the network. Adding it to `lintNote()` would surprise users running plain frontmatter linting. The command still respects `lintIgnoredFolders` via `linter.isPathIgnored()`. Automatic triggers (create/edit/paste) are off by default for the same reason. If you add a future "lint everything everywhere" command, opt it into attachment localization explicitly — don't fold it into `lint-note`.
- **Derived ID frontmatter keys are kebab-case singular/plural pairs**: `yt-video-id`/`yt-video-ids`, `post-id`/`post-ids`. The singulars are per-note metadata (one URL → one ID); the plurals are tracker-intake aggregates. `Lint: all` populates the singulars from the note's `source` field only — it never scans the note body, because the IDs are metadata about what the note represents, not about incidental URLs inside it. Existing notes with legacy snake_case keys (`video_ids`, `post_ids`) are migrated manually via `Lint: update property in vault`, which prompts for old/new key names and rewrites every frontmatter entry under `lintIgnoredFolders` filtering.
- **`post-id` canonicalization is platform-aware, not a blind param-strip.** `postIdFromUrl` in `src/orchestration/utils/blogs.ts` is the single chokepoint for both sides of blog dedup: the RSS/Atom parse derives a post's id from it, and the seen-set scan derives the same id from each note's `source` field (`feedSources.ts addSourceUrl`). They must agree, but email-notification links carry extra params the RSS bare slug doesn't (Substack: `publication_id`, `post_id`, `isFreemail`, `r`, `triedRedirect`, `utm_*`). We **cannot** strip all params blindly — on some sites a param like `article_id` *is* the identifier. So `auto` mode runs a `CANON_RULES` table keyed on URL *shape* (the Substack rule matches `/p/<slug>` **plus** a Substack signature param, then drops all params — works on custom domains like emilkirkegaard.com); only if no rule matches does it fall back to the conservative `TRACKING_PARAM_RE` denylist (unknown params preserved). The bare RSS slug has no signature param, so the rule doesn't fire there, yet both the slug and the stripped email link converge on the same `https://host/p/slug`. Override per-blog via the optional **Canon** column in the blogs table (`auto`|`substack`|`strip-params`|`keep-params`); `keep-params` is the escape hatch for sites where a param is the real id. The override reaches the note side (which has no blog context) through `buildBlogCanonHostMap` → a hostname→method map threaded into `buildFeedSeenIdSet`/`ingestFrontmatterIds` as `hostRules`. `lint.ts deriveSourceIdProperties` stays pure `auto` (no blog context); its derived `post-id` is cosmetic — matching correctness lives in the seen-set path, which re-derives from `source` every run, so fixing the canonicalizer repairs already-captured notes without a frontmatter backfill.
- **`localizeNote()` re-reads the file right before writing, and the materializing flag spans the whole async op — not just the write.** Remote attachment downloads inside `processMatch()` can take seconds to tens of seconds. If we kept the original read-once/write-once shape, any concurrent edit landing in that window (manual `Lint: all`, debounced auto-Lint at 2s, paste, sync, the user typing) would be silently overwritten when Localize finally called `vault.modify` with its stale buffer. The fix: build a list of `(match.original → newRef)` string replacements during the download loop, then re-read fresh content and apply the replacements to *that* before writing — the literal embed strings won't be touched by Lint, so the replacements remain valid. And `withMaterializing()` now wraps the entire op so the debounced auto-Lint / auto-Localize handlers in `src/main.ts` (which gate on `!isMaterializing`) stay suppressed for the full duration, not just the millisecond-long write. If you add another long async note-mutating command, follow the same shape.
- **The Localize attachment hash is a deterministic content MD5, not random.** `md5()` in `src/localizeAttachments.ts` hashes the *final post-conversion bytes* of each attachment, and `writeAttachment` feeds that into the `{{md5}}` filename token. It looks like a random string but is fully stable: the same bytes always produce the same `_MD5.ext` name, which is exactly what makes re-localizing idempotent (the `MD5_NAME_RE` gate in `processLocal` skips files already named/placed correctly) and dedupes identical content even when it arrives from two different URLs. Don't "fix" it to hash the source URL instead — that would break content dedup and re-localize stability, and it's intentional that conversion settings changing the bytes also change the hash. The trade-off (two URLs with byte-identical content collapse to one file; a URL whose bytes drift re-localizes under a new name) is the desired behavior.
- **Localize strips web-clipper `data:image` lazy-load placeholders, and they're invisible to `parseAttachmentRefs`.** Web clippers capture lazy-loaded `<img>` as *two* markdown images glued on one line: a 1×1 transparent placeholder `![](data:image/gif;base64,...)` immediately followed by the real image, separated by a space. Obsidian's metadata cache does **not** list `data:` URIs as embeds, so `parseAttachmentRefs` never sees them (`localizeNote`'s match list excludes them entirely — confirmed via Localize debug mode). Left in place, the placeholder shares an inline run with the real internal embed and **prevents Obsidian from rendering that embed at all** — the note shows no images even though Localize correctly downloaded every real attachment to a valid path. `localizeNote` therefore strips them separately via `DATA_URI_IMAGE_RE` (`![alt](data:image/...)` + trailing inline whitespace) as a post-pass on the fresh content, gated on `localizeAttachmentsImagesProcessAttached`. This is independent of the match/replacement loop, so the `matches.length === 0` early-return and the `replacements.length > 0` write-guard both also check `placeholderCount`. To diagnose "Localize ran but images don't show," enable **Localize → Debug mode** (writes to the shared `_crucible/debug.md`) and read the per-image decision lines.
- **Localize emits markdown embeds with an *empty* alt (`![](path)`), because Obsidian reads a numeric alt as a display size.** Obsidian parses `![1](img.png)` as "render at 1px wide" — the alt is interpreted as a width when it looks like a number (or `WxH`), so the image collapses to an invisible sliver. Localize's "alt" is only a guessed filename (`guessRemoteOriginalName` returns the last path segment sans extension — Patreon's `.../1.png` → `1`, which is exactly the poison value), so `formatEmbed` drops it entirely for the `md` branch. Don't reintroduce alt text into `formatEmbed` to "improve accessibility" — a numeric filename will silently break rendering again. Wiki embeds (`![[path]]`) never carried alt anyway.
- **YT video ID extraction has one home.** `extractVideoIdFromUrl` in `src/orchestration/utils/youtube.ts` owns the regex set (`watch?v=`, `youtu.be/`, `/shorts/`, `/embed/`). `canonicalizeUrl` in `src/orchestration/utils/urlCanonicalize.ts` delegates to it for the ID-extraction step while keeping its own URL-rewriting (host normalization, Shorts → watch, tracking-param strip). Don't add new YT regexes elsewhere — extend `URL_PATTERNS` instead. Shorts URLs and watch URLs yield the same ID, which is the load-bearing assumption behind dedup in `YoutubeTrackerWorkflow`.
- **The Ingestion Dashboard and the consolidation workflows share pure functions in `src/orchestration/utils/{blogsIntake,youtubeIntake}.ts`.** `buildBlogsSeenIdSet` / `buildYoutubeSeenIdSet`, `scanBlogsTrackerRuns` / `scanYoutubeTrackerRuns`, `loadConfiguredBlogs` / `loadConfiguredChannels`, and the intake-run listers are the single source of truth for "what is uncaptured" and "which intake runs exist." Both the dashboard and the `*_consolidate` workflows import them. If you change the algorithm, both surfaces follow — but keep them as pure `(app, ...)`-taking functions so the dashboard can call them outside a `WorkflowContext`. Don't reintroduce the logic inline in the workflow class.
- **`plugin.ingestionEvents` is the source of truth for "ingestion happened" signals.** `FileJobBackend` emits `tracker-run` after each blog/youtube tracker job finishes; the YouTube metadata fetch path (the `youtube_metadata_fetch` memory job, run by `MemoryJobBackend`, plus the standalone `fetchYoutubeMetadataForActiveNote` command) emits `metadata-enriched` after each successful write. The dashboard subscribes to these in addition to Obsidian's `metadataCache.on('changed')` / `vault.on(...)`. If you add a new ingestion path (e.g. a Web Clipper inbox watcher), emit the matching event from there too — the dashboard's live-refresh routing depends on it. `YoutubeMetadataFetchWorkflow` runs in two modes: with `params.targetPath` it calls `ingestYoutubeVideoMetadata` (writes the `yt-metadata` wikilink back onto the note); without one it calls `enrichYoutubeMetadataStandalone` (no back-link write). Don't pass a fake `TFile` to `ingestYoutubeVideoMetadata` — `fileManager.processFrontMatter` will throw.
- **The Orphaned Attachments dashboard section keys off the `_MD5` name convention, not the localize folder.** There is no single "Localize directory" setting — `localizeAttachmentsFolderTemplate` is a per-note template (default `{{folder}}/_attachments/{{slug}}`), so managed attachments are scattered vault-wide. `computeOrphanedAttachmentRows` in `src/ingestionDashboard.ts` therefore scans every vault file matching `MD5_NAME_RE` (exported from `src/localizeAttachments.ts`) of a localizable media type (`classifyLocalizeMediaType` in `src/utils.ts`), and flags those absent from `metadataCache.resolvedLinks`. Consequence 1: if a user changes `localizeAttachmentsNameTemplate` away from the `_MD5` suffix, their files won't be detected — keep the name template and the regex in sync. Consequence 2: `resolvedLinks` covers embeds and body links but **not** frontmatter property links (`frontmatterLinks`), so an attachment referenced only from a YAML property (e.g. `cover:`) can be falsely flagged; if that bites, union `getFileCache(f).frontmatterLinks` targets into the referenced set. Deletion uses `app.fileManager.trashFile` (vault trash), and "Cleanup all" routes through `ConfirmModal` (`src/confirmModal.ts`).
- **Daily Brief Lite FX comes from Frankfurter, and its autocompletes cache to settings, not memory.** The FX rate provider is `api.frankfurter.app` (`src/orchestration/utils/fx.ts`), *not* `open.er-api.com` — older UI copy claimed the latter. The currency/location pickers in `Crucible → Settings → Orchestrate → Daily Brief Lite` (`CurrencySuggest` / `LocationSuggest` in `src/suggesters.ts`) are backed by the same two providers: Frankfurter `GET /currencies` for the code list, and Open-Meteo geocoding (`geocoding-api.open-meteo.com/v1/search`) for `City, CC` + coordinates. Two non-obvious things: (1) both override `getSuggestions` as **`async` returning a `Promise`** — Obsidian's `AbstractInputSuggest` allows this, and `LocationSuggest` debounces live geocoding with a `sleep(250)` + `lastQuery`-still-current guard so each keystroke doesn't fire a request; (2) responses are **persisted to plugin settings** (`orchestrationDailyBriefCurrencyCache`, and `orchestrationDailyBriefGeocodeCache` keyed by normalized query), each entry stamped with `fetchedAt`, because these lists change rarely. The cache is invalidated only by the red **Clear cache** buttons next to "Add currency pair" / "Add location" — there is no TTL. If you add another rarely-changing external lookup here, follow the same settings-cache + manual-clear shape rather than a module-level in-memory cache.
- **One unified queue, two persistence backends — not two queues.** Every `JobType` declares `persistence: 'file' | 'memory'` in its `JobTypeConfig`, and `Orchestrator.register` builds the matching `JobBackend` (`src/orchestration/{File,Memory}JobBackend.ts`). `FileJobBackend` is the durable, vault-backed path: every job is a markdown file under `orchestrationQueueRoot/{inbox,running,done,failed}`, survives restarts, and is claimed/moved through `JobStore`. `MemoryJobBackend` is deliberately the opposite — an in-memory `MemoryJobQueue` (`src/orchestration/MemoryJobQueue.ts`) that dedupes by `dedupeKey`, auto-drains independent of the autorun toggle, emits live `enrichment-queue-updated` / `metadata-enriched` events, and forgets terminal entries after `terminalRetentionMs`; it **never** touches `JobStore`, because persisting transient UI state as on-disk jobs would spam the vault with throwaway files. The YouTube enrichment queue is exactly this: the `youtube_metadata_fetch` memory type (`youtubeMetadataJobConfig` in `jobTypeConfig.ts`), surfaced to the dashboard through the thin `EnrichmentQueueAdapter`. The two backends are *unified* under one runner: `OrchestrationAutoRunner` drains every type with the same per-type `MinIntervalGate` cooloff and the global `Semaphore` concurrency cap; `Orchestrator`/`AutoRunner` dispatch to `backend.enqueue/runNext/hasPending/refill` rather than branching on `persistence`. So: add a new persistence kind as a new `JobBackend`, not as a parallel queue with its own drain loop, and reuse `MinIntervalGate` for any request pacing rather than reimplementing the spacing math. (A file-backed job whose type later flips to `memory` is unrunnable until `scan()` re-homes it — see the re-home quirk below.)
- **`JobStore.move` rolls the rename back if the frontmatter write fails.** A job's queue bucket is determined by which folder its file lives in (`listFolder` reads by folder), and the frontmatter `status`/`updated` fields must agree with that folder. `move` renames the file into the target folder *then* rewrites the frontmatter; if that second write throws, the file is renamed back to its original path before the error propagates, so a job is never left moved-but-un-updated (e.g. sitting in `done/` while still claiming `status: running`). If you add steps to `move`, preserve the "leave the job fully in its prior bucket on failure" invariant.
- **`console.*` is banned in `src/` outside `src/log.ts`.** Crucible keeps the developer console quiet for users by default. Every diagnostic goes through `logWarn` / `logError` from `src/log.ts`, which no-op unless debug output is enabled (`setCrucibleDebug(true)` programmatically, or `window.__CRUCIBLE_DEBUG__ = true` in an installed vault). `grep -rna "console\." src/` should match only `src/log.ts`. Add new diagnostics via the helpers, not raw `console.*`.

  **Use the `-a`.** Without it this gate is not sound: a single NUL byte anywhere in a file makes GNU grep classify it as binary and *silently skip its contents* while still exiting 0, so a `console.*` call in that file passes the gate unseen. This is not hypothetical — `src/fileOpenRanking.ts` shipped a raw NUL in the `createNarrowState` sentinel (`filterSig: '<NUL>'`, written as a literal control character rather than the `'\0'` escape), and an injected `console.log` in that file was confirmed to evade `grep -rn`. The literal was replaced with the two-character escape `'\0'` — identical runtime value, plain-text file — but the gate keeps `-a` so the next stray control byte can't re-blind it. The same NUL also silently breaks any other `grep`-based sweep over `src/`, which is worth remembering when a search "finds nothing" implausibly.

  **It happened a second time, so treat "sentinel string" as the warning sign.** The vector-leg work wrote the vector backend's all-vaults cache key as a literal NUL (`cacheKey = vaultId => … : '<NUL>all'`) in `scripts/search-companion.mjs` — same idea as `filterSig`, same mistake, a different file outside `src/`. Symptom in review: `grep -n "MATERIALIZED" scripts/search-companion.mjs` returned **nothing** on a file that plainly contains it, and `file` reported `binary data` where `git show master:…` of the same file reported `Unicode text, UTF-8`. Note the byte was valid-UTF-8-clean (`raw.decode('utf-8')` succeeded) — only `file`/grep's binary heuristic caught it, so a UTF-8 validity check is not the test. When you need an in-band sentinel that cannot collide with real data, write `'\0'` (two characters) — never paste the control character. When a `grep` over a known-good file implausibly finds nothing, check `file` on it before believing the result.
- **`NoteLockManager.withLock` is re-entrant per async-execution context — and it has to be, because chains hold a note's lock while invoking lint/localize/yt-metadata steps that re-lock the *same* note.** The lock is a path-keyed FIFO mutex (`src/orchestration/NoteLockManager.ts`). `executeChain` wraps the whole step loop in `withLock(targetFile.path, 'chain:'+name, …)`, but chain steps can call internal commands (`lint-note`, `lint-cleanup-transcript`, `lint-localize-attachments-note`, the YT-metadata write) that *also* call `withLock` on the same path. With a plain mutex that's a guaranteed self-deadlock — the holder waits on a lock it already owns — which is exactly what stuck "Refine Transcript: Gemma 4" (the refined text was written, then the chain's lint/cleanup step blocked forever and the overlay spinner never cleared). The fix: `withLock` tracks held paths in an `AsyncLocalStorage<Set<string>>` and runs inline (no re-acquire) when the current context already holds the path. Reentrancy is **context-scoped on purpose** — a *foreign* `withLock` on a held path (a different top-level operation) is not in the holder's async context, so it still queues as a waiter; only nested calls within the holder re-enter. Two consequences: (1) low-level `acquire` is deliberately left non-reentrant — only `withLock` (what every mutation choke-point uses via `withOptionalNoteLock`) re-enters; if you add a new choke-point, go through `withLock`, not raw `acquire`. (2) This pulls in `node:async_hooks`, so `esbuild.config.mjs` externalizes both bare and `node:`-prefixed builtins (`...builtinModules.map(m => 'node:'+m)`); Electron's renderer Node resolves the `require("node:async_hooks")` at runtime.
- **A note-mutating command used as a chain step must be registered as a chain *internal* command, or it runs fire-and-forget.** `ChainManager.executeStep` resolves `step.commandId` against the internal registry (`registerInternalCommand`, populated by the `register(...)` helper in `main.ts registerInternalCommands()`). On a hit it `await`s the fn and passes `targetFile` (the chain's note). On a **miss** it falls through to the external branch — `this.app.commands.executeCommandById(step.commandId); return true;` — which is fire-and-forget: it does *not* await the command's promise, returns `true` immediately (so debug.md logs "success"), ignores `targetFile` (the command reads the *active* note), and runs **outside** the chain's note-lock context. That's how `youtube-fetch-video-metadata` (registered only via `registerCrucibleCommand`/`addCommand`, not as an internal command) silently no-op'd inside "Ingest as Transcript": every step logged success but the `yt-metadata` link never landed, because the real write happened after the step returned, as a foreign lock-waiter, and got lost — while running the command standalone worked. Fix pattern: register the command as an internal command too (`register('youtube-fetch-video-metadata', (_a,_p,_e,tf) => this.fetchYoutubeMetadataForActiveNote(tf))`), having its handler accept an optional `targetFile` that defaults to the active note, and return a boolean. The `register()` helper aliases both `obsidian-crucible:<id>` and `crucible:<id>`, so either stored `commandId` form resolves. If you expose another note-mutating Crucible command that users may drop into a chain, register it internally — don't rely on the external `executeCommandById` path for anything that writes. Audited coverage (all self-register an internal command taking `targetFile`): the lint family, `materialize-*-today`, `mark-as-forwarded`, `youtube-fetch-video-metadata`, the two move-file commands (`registerMoveFileCommands`), per-capture (`registerCaptures`), per-agent (`agents.ts registerAgents`), and per-chain — `registerChains` now also registers each `chain-<index>` as an internal command so a **nested chain** runs awaited, on the parent's target note, under the reentrant lock (it cleans up `registeredChainInternalIds` first so reordered/deleted chains don't leak a stale id). Intentionally **not** internal: the `materialize-*-picker` commands (interactive modal, no `targetFile` semantics) and the `move-current-file-to-folder...` picker — they prompt, so they don't fit the awaited-target-file chain-step model.
- **`mutating` is the single flag that decides whether running a command/chain takes the note lock, and the chain cycle-guard is keyed by chain *+ note*, not the chain alone.** Every registry entry carries `mutating` (`CrucibleCommandEntry` in `main.ts`; `registerCrucibleCommand` defaults it to `true`), and `Chain` has an optional `mutating?: boolean` (omitted === mutating, surfaced as the "Mutates the note" toggle in the chain editor). `executeChain` only wraps the step loop in `withOptionalNoteLock` when `chain.mutating !== false`; a read-only chain (e.g. one that just opens a dashboard view) runs without locking/graying the note. Default-true is deliberate — existing chains and any command you forget to mark stay safely serialized. Separately, the recursion guard is now `executing: Map<Chain, Set<string>>` keyed by the resolved target path, so the **same chain runs concurrently on different notes** (a queued `transcript_refine` on note A and a manual "Chain: Refine Transcript" on note B no longer false-trip the "already running; skipping" cycle notice) while a true self-cycle on the *same* note is still caught. Resolve `targetFile` *before* the guard check — the key needs the path. Don't reintroduce a chain-only `Set<Chain>` guard (false-positives across notes) or hoist locking out of the `mutating` check (re-grays read-only chains). The built-in lock-takers (lint, localize, yt-metadata) are inherently mutating and lock unconditionally; the registry `mutating` flag only drives the chain path today (read-only built-ins are marked `false` for documentation / future centralized dispatch).
- **The auto edit-triggers bail when the note lock is held — the lock, not `isMaterializing`, is the authoritative "this note is being mutated, hands off" signal.** `debouncedLint` / `debouncedLocalize` (the `vault.on('modify')` handlers in `main.ts`) now early-return on `this.noteLocks.isLocked(file.path)` *in addition to* `!this.isMaterializing`. `isMaterializing` is a **global** boolean that a long chain only sets around its own lint/localize sub-ops, so between an "Ingest as …" chain's steps it reads false; the debounced localize would then fire against a note the chain is mid-writing, download an attachment, and lose the landing ref when the chain's next write clobbered the buffer — leaving an orphaned `_MD5` file. Gating on the note lock makes the lock holder (the chain) the sole mutator; the auto-trigger simply skips while it's busy and the chain's own reentrant localize step still runs inline. If you add another auto-fired note-mutating handler, gate it on `noteLocks.isLocked(path)` too — don't rely on `isMaterializing` alone.
- **`fileManager.processFrontMatter` silently drops the value write when the metadata cache is stale — which it is right after a rename + rapid edit.** `processFrontMatter` merges the callback's mutations against `metadataCache.getFileCache(file).frontmatterPosition`, not the raw content. When the cache hasn't re-indexed the current bytes — e.g. the "Ingest as News" chain runs `move-current-file-to-daily-folder` then `lint-note` immediately after the web clipper wrote the note in staged bursts — the position is stale, so the merged frontmatter is written to the wrong byte range and the value is lost. Symptom that cost a long hunt: lint computed `word-count 380`, the callback's `fm['word-count']` *was* 380, yet the on-disk value came back empty; running `Lint: all` again seconds later worked only because the cache had settled (that was the user's standing workaround). The tell is that `processFrontMatter`'s own resulting `modify` event shows the value already wrong — no later clobber involved. The canonical fix is the **write-consistency barrier inside `updateFrontmatter`** (`src/frontmatter.ts`) — the chokepoint every frontmatter write must go through. Before calling `processFrontMatter` it compares the cache's `frontmatterPosition` end offset and key set against the actual block in the raw content; when they disagree it awaits the file's next `metadataCache.on('changed')` (bounded, ~2s — the write-side mirror of `TriggerRegistry.waitForConsistentCache`), and on timeout it warns, writes anyway, and verifies the mutated keys landed via a raw re-read (escalating the log if not). So: route every frontmatter write through `updateFrontmatter` and the race is handled for free — do **not** add per-key content-based reasserts (the old `setFrontmatterWordCount` workaround was deleted; its `String.replace` rebuild also corrupted empty frontmatter blocks). If a content-based `vault.process` fallback is ever genuinely needed, it must splice by index, never `String.replace(block, …)`. A separate belt-and-suspenders lives in `ChainManager.reconcileOpenEditor`: after a chain that moves-then-mutates a note, it forces any open editor leaf's buffer to match disk (`setViewData`) so a stale editor autosave can't clobber the chain's writes — relevant when the note *is* open (the clipper case leaves it closed, so that path is a no-op there).
- **A file-backed job whose `JobType` is now `memory`-persistence is unrunnable, and `scan()` re-homes it.** Job types declare `persistence: 'file' | 'memory'` in their `JobTypeConfig`. The runner dispatches per type to a `JobBackend`: `MemoryJobBackend` drains an in-memory `MemoryJobQueue` and **never** claims the file folders, while `FileJobBackend` claims markdown jobs from `queued/`. So when a type migrates from file to memory — as `youtube_metadata_fetch` did when enrichment folded into the unified queue — any markdown job left in `inbox/running/` becomes a permanent orphan: nothing drains it, and stale-running recovery only bounces `running→queued`, which is just as un-claimable (it stuck a `youtube_metadata_fetch` job in `running/` with the spinner never clearing). `Orchestrator.scan()` therefore sweeps `queued`+`running` for entries whose current `getConfig(type).persistence === 'memory'`, re-enqueues their params into the memory queue via that type's `backend.enqueue` (which kicks an immediate drain), and archives the markdown file under `done/` with a re-homed note. The heal runs on the **manual "Orchestrate: Scan queue" command only** — there is no auto-scan on load — so after changing a type's persistence, tell users to run Scan once (or run it yourself) to clear strays. If you flip another type to memory, this sweep already covers it; don't reintroduce a file-claim path for memory types.
- **`youtube_metadata_fetch` is one job per *note* (dedupe key `note:<targetPath>`), and the API fetch is the rare path — link-if-exists comes first.** The old shape (dedupe on `videoId`, single job vault-scanning `linkAllNotesForVideoId` to fan the `yt-metadata` link onto every matching note) is gone; don't reintroduce it. `youtubeMetadataJobConfig.dedupeKey` is `targetPath ? Because the metadata note is found-not-fetched on every job after the first, N duplicate captures cost one API call total. Standalone entries (uncaptured videos, no vault note yet) keep videoId keying (`video:<id>`) and skip the link write. Anything wanting "all notes for this video get linked" enqueues one per-note job per note (the dashboard's "Enqueue all" and the `yt-metadata-on-capture` trigger both do).

- **`fileManager.renameFile` on a folder does NOT rewrite links from a note renamed in the same tick — the metadata cache lags.** When a localized note moves folders, `AttachmentLocalizer.onNoteRename` (`src/localizeAttachments.ts`) moves its attachment folder with `fileManager.renameFile(folder, newFolder)` from inside the note's own `vault.on('rename')` handler. The read/modify is wrapped in `withOptionalNoteLock` + `withMaterializing` so it doesn't retrigger the debounced auto-lint/localize. In clip-then-ingest flows with auto-localize enabled, that automatic rewrite can race a Localize pass that has just shortened a long remote image URL to a local `_MD5` embed. Obsidian's rewrite is position/cache based, so stale offsets can splice the embed into nearby prose (e.g. `these days` became `th![](hash_MD5.webp)hash_tail.webp)`). `onNoteRename` now moves the attachment folder with `app.vault.rename(existing, newFolder)` specifically to bypass Obsidian's link-rewrite machinery, then performs the scoped embed-prefix rewrite itself under the note lock/materializing guard. - **`NoteLockManager` also locks non-note resources (`kind::id` keys), with a strict acquisition order: note lock BEFORE resource lock.** `withResourceLock(kind, id, …)` maps to `withLock(resourceLockKey(kind, id), …)` — the same FIFO mutex map, namespaced as `kind::id` (`:` is illegal in vault filenames, so a resource key can never collide with a note path). First user: `yt-video::<id>` serializes the check-then-create of a video's metadata note across per-note `youtube_metadata_fetch` jobs and the direct command, which would otherwise both miss `findExistingMetadataNote` and double-fetch/double-create. The ordering rule is the deadlock guard: code holding a note lock may acquire a resource lock inside it, but code holding a resource lock must NEVER acquire a note lock — note→resource everywhere means no wait cycle is possible. Reentrancy works across the nesting (both go through `withLock`'s `AsyncLocalStorage` held-set). Resource keys deliberately do not emit `note-lock-changed`: they drive no editor overlay, and listeners key off vault paths.

- **The note-lock follows renames; a mutating op that moves its target note mid-flight must not strand its lock under the old path.** The lock is keyed by path, but every gate that prevents concurrent writes reads the *live* path: `isLocked(file.path)` in the auto-lint/localize debounces (`main.ts`), `TriggerRegistry.fireEvent`, and `onNoteRename`'s own `withOptionalNoteLock`. An "Ingest as …" chain holds `withOptionalNoteLock(targetFile.path, …)` for the whole chain, then a step moves the note into the daily asset folder (`moveFileToFolder` → `fileManager.renameFile`). Before the fix the held lock stayed keyed under the *old* path, so all those gates saw the new path as unlocked and fired concurrently — the chain (writing frontmatter under the old-path lock) and a localize pass (rewriting attachment refs on the new path) interleaved, splicing a body `![](…_MD5.jpg)` embed into the `word-count` frontmatter field. Reentrancy and release track the `LockState` object (not the path), so re-keying is safe for the holder and a re-entrant `withLock(newPath)` from a later chain step still runs inline. If `newPath` already has its own lock (shouldn't happen — the mover checks the target is free), it logs and leaves both untouched rather than clobbering a holder.
- **LM Studio (and llama.cpp/vLLM/LocalAI) is the `openai-compatible` provider kind, NOT `ollama`.** The two local kinds speak different wire protocols: `ollamaClient` (`src/providers/ollama.ts`) POSTs to `<baseUrl>/api/chat` with Ollama-native JSON, while LM Studio serves the OpenAI wire format at `<baseUrl>/chat/completions`. - **The N1 Console theme (`theme/`) and the plugin are a matched set — the plugin drives a *third* light/dark axis Obsidian doesn't natively have.** Obsidian only knows binary `.theme-dark`/`.theme-light` and runs one theme at a time, but the N1 Applied design system has a three-way **surround** (dark / med / light, Med default). A pure theme can't express the third state, so Crucible provides it: `applySurround` (`src/surround.ts`) writes `document.body.dataset.surround`, and `theme/theme.css` keys every token off `body[data-surround="…"]`. This takes a user off "Adapt to system" appearance the moment they set a surround. Break that split and the two (0,1,1) blocks start fighting on source order. Consequence: Settings → Appearance → Accent color goes inert while this theme is active; change the accent by editing the three `--n1-accent-ui-*` triples in block 1 instead. A broader `!important` sweep is wrong — every other mapping already wins on specificity alone — and will be reverted. (8) The `--n1-*` values in `theme.css` are a **vendored snapshot** of the (mid-rename) design-system tokens (`7als_art_direction/packages/signalworks/css/tokens/*`); `theme/README.md` documents the source + re-vendor flow (a one-file edit of the three `body[data-surround]` blocks — do not add a build step or duplicate token files). Because the server has zero npm dependencies, the `Dockerfile` copies exactly one file and skips `package.json`/`node_modules` entirely; adding an install step or downgrading the base image below 24 breaks the `node:sqlite` import silently (it throws at the `import` line, not at some later call site). Don't "helpfully" add a `package.json` copy or an install step just because that's the usual shape of a Node Dockerfile — this one is dependency-free by design. **`.dockerignore` is load-bearing for the same reason**: without it the build context drags in `node_modules/`, the 2.8 MB `main.js`, and the multi-hundred-MB `.crucible/search.sqlite`, none of which the image needs.
- **The companion's listen host defaults to loopback (`127.0.0.1`) everywhere except inside the container.** `scripts/search-companion.mjs` reads `--host` → `CRUCIBLE_SEARCH_HOST` → `'127.0.0.1'`, and the standalone `npm run search:serve` path relies on that default staying loopback-only — the API is unauthenticated with full index write access, so a loopback bind is the whole security boundary for a bare `node scripts/search-companion.mjs` run. Only the `Dockerfile`/`docker-compose.yml` set `CRUCIBLE_SEARCH_HOST=0.0.0.0`, because a loopback bind *inside* a container is unreachable from the host even with a published port — that's a container-only override, not a new default. Don't flip the script's own default to `0.0.0.0` to "simplify" the container case; that would silently expose every non-containerized run.
- **The companion's pooling CTE must stay `MATERIALIZED`, and its FTS schema migrates itself.** `/v1/search` ranks one row per *path*, not per chunk: a `matched` CTE scores chunks with weighted bm25 (`bm25(chunks_fts, 0,0,0, 10.0, 5.0, 1.0)` — title ≫ heading ≫ text), then a `pooled` CTE collapses to `GROUP BY path` on `MIN(score_text)`. Three non-obvious things hold it together. (1) **`WITH matched AS MATERIALIZED` is load-bearing, not a hint** — without it SQLite flattens the CTE into the aggregate query and `bm25()`/`snippet()` throw `unable to use function bm25 in the requested context`, because FTS5 auxiliary functions are illegal in an aggregate context. (2) The winning chunk's `id`/`heading`/`snippet` ride along for free because SQLite takes bare columns from the row that produced the `min()` when a query has exactly one `min()`/`max()` aggregate — a second aggregate (`COUNT(*)`) doesn't break that, but adding a second `min()`/`max()` would. (3) `COUNT(*) OVER ()` is evaluated before `LIMIT`, which is what let the duplicate `COUNT(*) MATCH` query (it doubled FTS work on every search) go away while `total` stayed the distinct-path match count. Separately, `chunks_fts` now carries FTS5 `prefix='2 3'` (schema version **2**), which `CREATE VIRTUAL TABLE IF NOT EXISTS` will *not* retrofit onto an existing database — so `migrateFtsSchema` drops and refills the FTS table from `chunks` on startup (lossless: `chunks` holds every indexed column). The client's half of that contract is `SEARCH_REQUIRED_SCHEMA_VERSION` in `src/search/types.ts`: a companion reporting a lower `schemaVersion` is flagged `rebuildRequired` (health goes `ok:false`, so auto-indexing defers; search still runs and says "index rebuild required"), because an older *binary* is the one mismatch no server-side migration can fix. Bump both together. Finally, the companion exports its pure helpers and guards the server bootstrap behind `isMainModule()` so `tests/searchCompanionRanking.test.mjs` can import it without opening a database or binding a port — keep new side effects inside `startServer`.

- **Counting "how many notes are in the vault" by globbing `*.md` is wrong by ~7.7x here — the queue's own job files dwarf the real corpus.** `_crucible/orchestration/queue/{done,failed}` accumulates one markdown file per orchestration job (17,206 done + 2,027 failed at the time of writing), so the vault's 42,042 `md`/`qmd`/`txt` files are **37,081 job files** plus only **~5,456 genuinely indexable notes**. `_crucible` is search-excluded by default (`defaultExcludedFolders` in `src/exclusions.ts`), so `SearchManager.listIndexableFiles` correctly reports the small number — a full rebuild enqueuing ~55 jobs rather than the expected hundreds is the *right* answer, not a truncated scan. The file-open-palette plan was sized against the inflated figure and set `SEARCH_REBUILD_BATCH_FILES = 250`; it is now 100. Two traps when re-measuring: use `find -L` (the vault symlinks `docs/` and every `initiatives/*/{README.md,INITIATIVE.md,FEEDBACK.md,plans}` in from their repos — plain `find` misses ~495 files Obsidian indexes), and remember `SearchManager.indexFiles` returns `upsertedFiles`, i.e. files whose **content hash changed**, so a job reporting "58 files" out of a 250-path batch is reporting a mostly-unchanged re-run, not dropped work.

- **The search client has two timeouts on purpose, and a mid-operation failure must not latch the availability gate like a failed probe.** `src/search/client.ts` keeps the interactive `SEARCH_SERVICE_TIMEOUT_MS` (5s, health + search — the UI must stop waiting on a dead companion) separate from `SEARCH_SERVICE_INDEX_TIMEOUT_MS` (60s, reset/upsert/delete/fileStates). Do not collapse them back into one constant: an upsert carries hundreds of chunks and is issued from the same main thread that synchronously chunks the batch's files, so the timeout races *local* work, not just the server's — under the old uniform 5s a healthy container (measured: ~53ms per 500-chunk flush server-side, 0 restarts, clean logs) was declared unreachable partway through the first full rebuild. The second half of that failure was the latch: `markCompanionOffline` used to call `markOffline`, whose `SEARCH_OFFLINE_CACHE_MS` is **5 minutes**, so one spurious timeout made every remaining batch job defer *without ever asking the companion again*, and each Obsidian reload drained exactly one more batch. Mid-operation failures now go through `CompanionAvailabilityGate.markTransientFailure` (`SEARCH_TRANSIENT_OFFLINE_MS`, 5s) and carry the thrown message as the gate's reason — without it `searchDeferredResult` falls back to "not reachable at <url>. Start it with: home-compose up crucible-search", which sends the user to restart a container that is already healthy. Keep `markOffline` for probe-confirmed outages only. Relatedly, `scripts/search-companion.mjs` now `console.error`s before returning its catch-all 500: the client turns any 5xx into `SearchServiceUnavailableError` → "companion not reachable", so a request that failed on its own merits used to be indistinguishable from a down container while `docker logs` showed nothing at all.

- **Companion search latency is governed by how much of the index the query matches, not by index size — so a short query is catastrophically slower than a long one, and the modal's 3-character type-ahead gate is the mitigation.** Measured medians for `/v1/search` against the live 52,257-chunk / 5,453-path index: `"c"` **733ms**, `"cr"` **239ms**, `"cru"` **27ms**, `"cruc"` **11ms**, `"crucible"` **5ms**, `"orchestration queue"` **2ms**. The shape is not a warm-up artifact — it is the `matched` CTE having to bm25-score every matching chunk before `pooled` collapses it to one row per path, and the trailing term is prefix-expanded (`term*`, the FTS5 `prefix='2 3'` index), so one or two characters match most of the corpus. Hence `SEARCH_TYPEAHEAD_MIN_QUERY_LENGTH = 3` in `src/search/debounce.ts`: below it `VaultSearchModal` does not fire automatically at all, though **Enter still forces any query through** — the gate paces typing, it does not restrict what may be searched. Don't lower it to 2 without re-measuring (2 chars costs ~9x 3 chars). Length is a proxy, not the real variable: a *common* short word stays expensive above the gate (`"the"` **827ms**), which is why `runSearch` also stamps each issue with a `searchGeneration` and discards a response whose generation is stale — with type-ahead, a broad early query outliving a narrow later one is routine, not theoretical, and without the guard the slower, less-specific results land last and win. Sweep mode deliberately opts out of type-ahead entirely (a project brief is not refined keystroke by keystroke, and each sweep costs a query expansion plus a wider result set). Relatedly, `SearchManager` now caches the link-boost graph and drops it from the `metadataCache.on('resolved')` handler in `main.ts` rather than rebuilding per search: `buildLinkGraph` walks all of `resolvedLinks` plus every file's `frontmatterLinks` for ~70ms here — tolerable once per explicit search, but more than the entire companion round-trip for a typical query, and per-keystroke it would be the whole latency budget. `'resolved'` is the correct invalidation event because it is precisely "link resolution has settled after an edit"; a briefly stale graph is harmless because the boost only reorders an existing result set and can never add or remove a result.

- **Obsidian's own "Excluded files" list is honored on both Crucible file surfaces, but asymmetrically on purpose: the search index *hides* those paths, the file-open palette *deranks* them.** `metadataCache.isUserIgnored` (Settings → Files & links → Excluded files) is declared in the `MetadataCache` augmentation in `src/types.ts` and used unguarded — `FileSuggest`/`FolderSuggest` (`src/suggesters.ts`) and `src/folderPicker.ts` have always filtered on it, so before this the palette and search were the two surfaces that silently ignored it. Search now folds it into `SearchManager.isExcludedFromIndex`, the single predicate behind `prepareFile`/`deletePath`/`listIndexableFiles`, alongside `isSearchIndexablePath` and `isPathExcluded(…, 'search')`. The palette instead ORs it into `FileOpenIndex.isIgnoredPath`, which sets `FILE_OPEN_FLAG_IGNORED` and costs the row a flat rank penalty larger than any tier gap — the row stays live and reachable by typing its exact name. That asymmetry is the design, not an oversight: a palette exists to reach a file you can name, whereas a search hit you did not ask for is noise. **Two consequences.** (1) Like `isPathExcluded`, the search filter is **index-time only** — adding a path to either exclusion list stops future indexing but does not retroactively purge rows already in the companion database; run `Orchestrate: Search rebuild index` to drop them. (2) `FileOpenIndex.exclusionSig` must include the raw `userIgnoreFilters` list (read through the presence-guarded, undocumented `vault.getConfig`, per the `src/surround.ts` precedent), because that list is edited inside Obsidian's own settings — no vault event fires and `plugin.settings` never changes, so without it in the fingerprint every IGNORED flag would stay stale until something else invalidated the snapshot. A build lacking `getConfig` degrades to the previous signature rather than throwing.

- **The search companion's vector leg is dimension-agnostic by design, scans the full matrix by requirement, and every number below is measured — don't re-derive them.** `plans/semantic-vector-leg-and-reranker.md` has the full argument; this is the operational summary a future session needs before touching `scripts/search-companion.mjs`'s vector code or `src/search/SearchManager.ts`'s embedding lifecycle.
  - **Dimension-agnostic, and the reason is a settings fact, not a technical one.** `searchEmbeddingModel` is a plain `ProviderModelRef` user setting — Crucible ships publicly, so no model (and no English-only assumption) may be compiled in. The companion therefore stores whatever width arrives (`embedding BLOB` + `embedding_dim INTEGER` + `embedding_model TEXT`, schema v3), records the producing model per chunk, and refuses to silently mix vector spaces inside one vault. **A width conflict at *upsert* time is a 4xx, never a 5xx** — `prepareChunkEmbedding`/`normalizeEmbedding` throw `HttpError(400, …)` on a non-finite/zero/empty/wrong-array embedding, and the vault-wide width check at `scripts/search-companion.mjs:909` throws 400 specifically because the client (`src/search/client.ts`) turns any 5xx into `SearchServiceUnavailableError` — "the companion is not reachable" — which would send a user to restart a container that is already healthy over what is actually a client-side model-mismatch bug. A width conflict on the *query* side is handled differently and deliberately isn't a 4xx at all: `runVectorLeg` (`:609`) pre-checks the query embedding's width against the vault's and, on mismatch, sets `outcome.note` and skips straight to FTS-only (`mode: 'fts'`) rather than failing the whole search — failing a request outright over a mid-model-switch mismatch would be worse than answering with keywords alone.
  - **The scan covers the FULL matrix, never the FTS candidate pool — this is the one mistake that passes every other test.** Reranking FTS candidates by vector similarity cannot surface a note sharing no keywords with the query, which is the entire reason the vector leg exists; a pool-reranking implementation looks correct everywhere else. The named regression test is `tests/searchCompanionVector.test.mjs`'s `'the vector scan covers the FULL matrix, not the FTS candidate pool: a chunk with zero keyword overlap still surfaces'` — it asserts a chunk with zero keyword overlap and a near-identical vector appears in results, with `attribution.textRank === null` and a real `vectorRank`. Do not "optimize" the scan to only touch bm25's candidate set.
  - **The measured numbers** (52,257 chunks, single-threaded JS, `Float32Array` full scan, brute-force cosine — vectors are stored L2-normalised so cosine is a dot product): KNN itself is **13ms at 384d, 24ms at 768d, 33ms at 1024d**, 214MB resident at 1024d. The interactive ceiling this puts on the design is **~250k chunks (~26,000 notes)** — past it, the dependency-free escape hatches are, in order, worker-sharding the scan over a `SharedArrayBuffer` (the matrix is already one flat `Float32Array`) and then `int8` quantization with a float32 rescore of the top ~1000 once residency (not latency) binds. **`int8` is not used today because it measured *slower* in scalar JS** — 19.6ms vs 12.4ms at 384d, no SIMD path to make up the difference — so it's the move for memory pressure, not speed. Separately, the in-memory matrix is dropped on every write and rebuilt lazily on the next vector search (Assumption 8: rebuilt, not patched, because patching can drift and rebuilding can't); that lazy build costs **391ms at 384d, 799ms at 1024d** (reading 52,257 BLOBs + memcpy). Invisible in normal use (one rebuild amortised over many subsequent searches per edit), but during an active backfill every batch invalidates it, so a search mid-backfill pays **~0.8s at 1024d** — that measurement is the trigger value for the deferred incremental-append fallback (not built; adding it uninvited would widen the vector backend's seam contract for a case that doesn't exist yet).
  - **The 12-thread ceiling and why `enrich`'s 301 events/s does not transfer.** `bge-small-en-v1.5` measured **3.8 chunks/s at 1 thread, 10.3/s at 4, 20.1/s at 12** (torch's default thread count on this 24-logical/12-physical-core box) — only 5.3× scaling from 1→12, so the box is already near saturation and there is no hidden 12× left to recover by throwing more threads at it. `news-ingestion/enrich`'s frequently-cited "301 events/s" for the same model on the same CPU is **not a contradiction and not transferable** — it's measured over short texts (a title line + a body line), and re-measured against realistic ~1,118-character vault chunks the number is 20.1/s: **15× apart purely on sequence length**. Don't cite `enrich`'s throughput as a projection for anything embedding vault-sized chunks.
  - **The coverage-aware skip, and its three fail-closed rules.** `SearchManager.indexFiles`'s skip condition (`:237`) is `contentHash matches **and** embeddingCoverageSatisfied(stored)` — content hash alone only proves the *text* hasn't changed, not that vectors exist or match the active model, so before this fix flipping `searchSemanticEnabled` on left every already-indexed file permanently vector-less with no error. `embeddingCoverageSatisfied` (`:337`) enforces: (1) **partial coverage is not coverage** — `hasEmbeddings` is `chunkCount > 0 && embeddedCount === chunkCount` server-side (`scripts/search-companion.mjs`'s `/v1/files/state`), so an interrupted backfill's partially-embedded path is correctly re-queued rather than treated as done; (2) **unknown coverage counts as uncovered** — a `hasEmbeddings === undefined` response (an older companion that doesn't report the field) re-indexes rather than skips, because skipping a file that actually needs work is a silent permanent gap while re-indexing a file that didn't need it costs one read; (3) **with semantic off, coverage leaves the skip condition entirely** — `activeEmbeddingModelId()` (`:321`) returns `null` when `searchSemanticEnabled` is false or no model is picked, and `embeddingCoverageSatisfied` short-circuits to `true` in that case, so an FTS-only vault skips exactly as it always did rather than every file looking permanently stale and re-upserting itself every pass.
  - **`SCHEMA_VERSION` and `SEARCH_REQUIRED_SCHEMA_VERSION` are bumped together (now 3, per the existing pairing rule in this file), and the FTS migration is independent of that bump.** `migrateFtsSchema` (`scripts/search-companion.mjs:162`) keys on whether `chunks_fts`'s stored SQL already contains `prefix=`, not on `SCHEMA_VERSION` — so the 2→3 embedding-storage bump did **not** trigger an FTS drop/refill; only the earlier 1→2 `prefix='2 3'` change did, and would again on a hypothetical schema-1 database. The 2→3 migration itself is three additive `ALTER TABLE chunks ADD COLUMN` statements (`embedding BLOB`, `embedding_dim INTEGER`, `embedding_model TEXT`, `:149-151`) — no drop/refill of `chunks`, and nothing to backfill on upgrade since `searchSemanticEnabled` has always defaulted false (zero embeddings existed anywhere before this landed). The legacy `embedding_json` column from schema 1/2 is deliberately left in place on a migrated database rather than dropped — it's never read or written again and dropping it would mean a table rebuild for nothing.
  - **The vector backend is a narrow, injectable seam on purpose — `{ name, stats(vaultId?), knn(vaultId, queryVector, k), invalidate(vaultId?) }` — and nothing outside `createVectorBackend` may assume a flat array or an in-process scan.** That's what makes the two documented escape hatches (a `vec0`/sqlite-vec backend, a worker-sharded backend) a swap of this factory rather than a rewrite of `runSearch`/`fuseSearchRows`. It's a factory function inside `scripts/search-companion.mjs`, not a separate file, because the Dockerfile `COPY`s exactly one file — a second script file would silently break the container image build. If a separate file is ever wanted, it needs a Dockerfile change in the same commit.

- **A chunk id is unique only *within* a vault — every companion statement keys on `(vault_id, id)`, and one that keys on `id` alone is a data-loss bug, not a style nit.** `stableChunkId` (`src/search/chunker.ts`) derives an id from the note's path, ordinal and heading, so two vaults holding the same note at the same path minted the *same* id. The companion's `chunks` table was `PRIMARY KEY (id)` and the upsert conflicted on `id` alone with `vault_id = excluded.vault_id` in its SET list, so indexing vault B silently **re-labelled vault A's row as B's**: A's file then vanished from A's own (correctly vault-scoped) `/v1/files/state`, A's search stopped returning it, and a `/v1/index/reset` of *B* deleted A's data along with B's. Reproduced against an in-memory database running the real `createSchema` + `createRequestHandler`, not inferred. It was silent and partially self-healing, which is worse: A's next sweep saw the path missing, re-chunked it and stole the row back, so two vaults on a timer ping-pong the same rows forever, each intermittently missing the colliding notes, with no error anywhere. `docs/search-companion.md` had specified `vaultId + chunkId` keying the whole time — a user following the documented "multiple vaults can share one companion database" landed straight in it. The fix is both halves: `stableChunkId` folds `vaultId` into its hash (readable prefix unchanged — the id is still `path#ordinal:hash`), and schema **5** rebuilds `chunks` with `PRIMARY KEY (vault_id, id)`. **Do not reintroduce an `id`-only chunk statement** — the four that were wrong are the upsert's conflict target, the `chunks_fts` delete, `HYDRATE_CHUNK_SQL` (an id-only hydrate is a cross-vault *content leak*, not just a wrong snippet), and the FTS→`chunks` join; the last two were safe only because ids happened to be globally unique. `tests/searchVaultIsolation.test.mjs` is the barrier, and it is the first test in the suite to write two distinct `vaultId`s into one database — every other companion test pins a single constant, which is exactly why nothing caught this. Three notes on the migration (`migrateChunksPrimaryKey`): (1) it is a **lossless table rebuild, not a reindex** — SQLite cannot `ALTER` a primary key, so it creates the replacement, `INSERT ... SELECT`s every column plus the `rowid` across, drops, renames, then drops and refills `chunks_fts` in the same transaction (the `migrateFtsSchema` precedent); embeddings ride across untouched and nothing re-embeds. (2) The copy **cannot** lose a row, and the proof is from the old constraint rather than from the data: `id` unique across the whole database implies `(vault_id, id)` unique. Measured 2.7s over a synthetic 52,257-chunk / 1024d index. (3) It carries forward any column the current shape no longer declares (today only the vestigial `embedding_json`) rather than dropping it, and the reads happen *after* the additive `ALTER`s, so a schema-1 database migrates in one startup. Per the pairing rule, `SEARCH_REQUIRED_SCHEMA_VERSION` moved to 5 too — so between a plugin update and a container rebuild, health reports `ok: false` and search is **unavailable, not degraded**. Rebuild the companion image in the same landing.
